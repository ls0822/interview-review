# 专家级掌握深度（生成默认标准）

所有 **新建 / 重写 / 加深** 的知识点与配套问答，默认按本标准生成。目标读者：资深 Android / SDK 面试（能扛追问，不是背词条）。

## 深度档位

| 档 | 含义 | 题库要求 |
|----|------|----------|
| P0 必会 | 开口就要讲对的边界 | 原理 ≥ 5 点；坑 ≥ 4 条带追问；例子含正/错路径 |
| 专家加分 | 被追问 why / 边界时拉开差距 | 机制讲到「为何如此设计」；对比至少一种替代；失败模式说清 |

一篇 knowledge **默认同时覆盖两档**：正文以 P0 为主干，专家点写进原理后段或坑的追问里，并在 roadmap/组成里标清档位（若有）。

## knowledge 专家自检（写完必须全过）

1. **一句话**：闭卷 10 秒开场；含本质差异（不是定义翻译）。
2. **组成**：零件齐全，关系一眼可见；禁止只有名词列表无关系。
3. **原理**：  
   - 先直觉隐喻，再机制，再边界/失败  
   - 至少回答：正常路径、异常/取消/并发边界、和易混概念的差别  
   - 禁止纯 API 罗列；每点只推进一步  
4. **使用**：落到 Android / 库 / SDK 场景；写清「不该怎么用」。
5. **例子**：最小可推演；必须有一条**错误对照**。
6. **画面**：可口述草图（ASCII）；结构复杂则加 SVG（UTF-8 合法）。
7. **坑**：每条「错法 → 为何错 → 追问句」；至少覆盖并发/生命周期/性能/语义误解之一。
8. **先修**：`requires` / `order` 填全；不假设读者会先修外概念。

## qa 专家自检

- 问法像面试官；答案先结论后机制。  
- 至少预埋 1 个追问点（边界/对比/失败）。  
- 不复制整篇 kp；可 `knowledge_ref`。

## 明确不够专家的写法（禁止交卷）

- 只有定义 + 一两句「用于…」  
- 原理少于 4 个实质点，或全是条目名  
- 例子只有 API 签名没有推演  
- 坑没有追问，或只写「要注意」  
- 与官方语义冲突却不标注前提  

## 与「最小改动」的关系

- 日常按标注修改：仍最小改动，但**改到的段落必须抬到本标准**。  
- 用户明确要求「专家级全库梳理 / 重生成」：允许按模块重写 `_full/`，仍须过结构校验与本自检。

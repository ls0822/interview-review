## 一句话

对称加密同一把钥匙加解密，快，难在钥匙怎么安全地交到对方手里。非对称加密是一对公钥和私钥，用来交换钥匙或签名验签，不适合拿来加密大段数据。摘要把任意内容收成一段短指纹，用来看有没有被改过，不能代替加密，更不能拿 MD5 存密码。

## 组成与结构

| 种类 | 钥匙 | 能做什么 | 不能做什么 | 常见算法 |
|------|------|----------|------------|----------|
| 对称 | 双方同一把 | 加密大量数据 | 安全地第一次交换这把钥匙 | AES |
| 非对称 | 公钥可公开，私钥自己留 | 公钥加密小块数据、私钥签名 | 高速加密大文件 | RSA、ECC |
| 摘要 | 没有钥匙 | 完整性指纹 | 保密、证明是谁发的 | SHA-256；MD5 只适合兼容旧校验 |
| 慢哈希 | 带盐，故意算得慢 | 存密码 | 校验文件、传输加密 | 专门的密码哈希，而不是 MD5 |

HTTPS 把三者放在一次通信里：证书和非对称（或密钥交换）解决「钥匙给谁、对方是谁」，对称加密解决「页面和接口的字节」，摘要或 AEAD 解决「密文有没有被改」。离线包是另一条线：包体可以对称加密，再用摘要做完整性；上传则对文件做 MD5 或 SHA 采样校验，看传上去的是不是本地那一份。

## 原理（深度，分步骤，讲清为什么）

**1. 对称加密为什么快，钥匙为什么难**

AES 这类算法用同一把钥匙把明文变成密文，再变回来。运算适合长数据，文件和网络流都能用。谁拿到钥匙谁就能解。难题不在算法，在第一次怎么把钥匙交给对方：如果钥匙和密文走同一条会被窃听的通道，加密就没有意义。所以钥匙要么事先约定（离线包可以随更安全的通道下发钥匙或用用户态密钥包装），要么在 TLS 里用密钥交换现协商一把只用这一次的对称钥匙。

模式也有关系。同一把钥匙如果用固定方式加密重复内容，相同的明文块会变成相同的密文块，仍然会泄露规律。工程上用带初始向量的分组模式，或直接用同时提供完整性的 AEAD。初始向量不必保密，但不要每次都用同一个。面试不必背所有模式名，要知道「只有钥匙、没有完整性和随机化，密文仍可能被摆弄」。

**2. 非对称为什么只碰小块数据**

公钥加密，只有对应私钥能解。私钥签名，任何人用公钥都能验证这是私钥持有者签的，而且签的是这段内容。两件事方向相反：加密是为了不让别人看，签名是为了让别人确认是谁、内容没被换。

RSA、椭圆曲线比 AES 慢几个数量级，而且一次能加密的长度有限。所以 TLS 不用公钥去加密整个 HTTP 响应，只用它来证明身份、保护一小段密钥材料。公钥可以放进证书发给所有人。私钥出了服务器或写进客户端安装包，就等于没有私钥。

**3. 摘要为什么不是加密**

摘要是单向的：从内容能算出指纹，从指纹算不回内容。内容改一个字节，指纹就变。文件下载后重新计算摘要，和服务器给的对比，不一致就说明传坏了或被换了。这不保密。谁都可以对同一文件算出同一个 SHA-256。把摘要当成「加密后的密码」是错的：它没有钥匙，而且相同密码的摘要永远相同。

MD5 和 SHA-1 已经能被人为构造碰撞，安全场景不用它们做签名。传文件时如果协议历史就是 MD5，可以当一种校验和继续用，同时不要假装它还能防恶意伪造。材料里的上传校验就是采样算 MD5，目的是发现传输损坏和明显不一致，不是代替 TLS。

**4. 密码为什么不能只存 MD5**

密码库泄露后，没有盐的 MD5 可以用现成字典直接比对。盐是每个用户一段随机数，和密码一起哈希，相同密码也会得到不同结果，防止一张彩虹表打全部用户。哈希还要慢，否则攻击者可以高速尝试。所以密码存储用专门的慢哈希加盐。MD5、SHA-256 再加盐也不够慢。登录接口本身仍要走 HTTPS，慢哈希解决的是「库丢了之后」，不是传输。

**5. 防重放为什么摘要也不够**

攻击者可以把一整段合法请求原样再发一次。摘要仍然对，签名也仍然对。要在内容里放一次性 nonce 或时间戳，服务器记住用过的 nonce，或拒绝太旧的时间戳。这和加密是正交的：加密防看，签名防改和抵赖，nonce 防再放一次。

**6. 和证书锁定的关系**

锁定的是证书或公钥的指纹，指纹就是摘要。客户端只接受这个指纹，即使用户安装了别的根也不行。换证书就要更新指纹，否则旧客户端全部连不上。指纹可以随配置下发，避免每次换证都发版。

## 使用与实践

全站 HTTPS，不要自己用 AES 把整个通道重做一遍替代 TLS。TLS 已经解决了钥匙交换和完整性。业务上额外加密的是 TLS 终止之后仍不能明文落地的字段，例如落盘的离线包、日志里本不该出现的身份信息。

钥匙放在安全存储或由服务端按会话下发，不要写在仓库和安装包的常量里。客户端里的钥匙只能提高随便翻包的成本，不能当成服务器私钥。

日志脱敏：token、手机号、密钥材料不进日志。回捞日志有开关、脱敏和体积上限。

上传：分片可以各自带校验，整文件再做一次。校验失败就丢弃这一片重传，不要把对不齐的文件报给服务器说成功。离线包：加密包下载完先校验再解密再替换本地版本，任何一步失败都回滚到旧包。

密码只走慢哈希加盐，放在服务端。客户端可以做长度和复杂度检查，不要在本地只存一份 MD5 当登录凭据。

## 例子（至少 1 个完整代码或伪代码块 + 边界场景）

离线包先校验摘要，再解密，两步都过才替换本地文件。钥匙不写死在代码里，而从一次已经走 TLS 的配置接口来：

```kotlin
fun installPackage(file: File, expectedSha256: String, key: SecretKey) {
    val actual = sha256(file)
    if (!actual.equals(expectedSha256, ignoreCase = true)) {
        file.delete()
        throw IOException("checksum mismatch") // 不要解密，也不要替换正在用的包
    }
    val plain = aesDecrypt(file, key) // IV 从包头读，不重复使用固定 IV
    val stage = File(file.parent, "next.pkg")
    stage.writeBytes(plain)
    if (!stage.renameTo(activeFile())) {
        stage.delete()
        throw IOException("replace failed") // 旧包还在
    }
}
```

上传采样不是只算第一片：

```kotlin
fun verifyUpload(parts: List<File>, whole: String): Boolean {
    if (parts.any { md5(it) != serverMd5Of(it) }) return false
    return md5Concat(parts) == whole
}
```

边界一：只做了 AES，没有完整性。攻击者改了几个密文字节，解密出来是乱的 JSON，客户端当成解析失败反复重试，或者更糟，改到了刚好仍能解析的字段。加密要用带认证的模式，或者加密后再带独立的摘要并先校验。

边界二：摘要对上了但内容是别人的旧包。摘要只能说明「和这份指纹一致」。如果指纹本身被换成了旧版本的指纹，你会装回旧包。指纹要和版本号一起走可信通道，例如 HTTPS 接口返回版本、URL 和摘要，不能只信包里自己带的摘要。

边界三：密码表用无盐 MD5。两个用户密码相同，库里的值也相同，泄露后整表可被字典恢复。改成每用户随机盐加慢哈希。已经泄露的 MD5 无法反向升级成安全存储，只能强制重置。

边界四：nonce 没记。请求被抓包原样重放，签名仍通过，积分被加了两次。服务器要存最近用过的 nonce，或把 nonce 和业务单号绑成一次性。

## 画面（text 结构图）

```text
HTTPS
  证书（公钥 + 域名，CA 签名）
       → 密钥交换得到这一次的对称钥匙
            → AES 加密业务字节
                 → AEAD / 摘要 发现被篡改

离线包
  HTTPS 拿到 URL、版本、摘要、钥匙材料
       → 下载密文
       → 先对摘要
       → 再解密
       → 替换本地；失败则旧包还在

上传
  分片各自校验 + 整文件校验
  对不齐就重传这一片，不报成功

密码
  慢哈希 + 每用户盐     不是 MD5
```

## 常见坑与追问（至少 3 条）

1. **对称和非对称能不能互相替代？** 不能。对称适合大数据，但钥匙分发是问题。非对称适合分发钥匙和签名，但慢、还能加密的块很小。HTTPS 两个都用，各干一段。

2. **MD5 能当密码存储吗？文件校验还能用吗？** 密码不行，没有盐又太快，泄露后可被字典恢复。文件校验在旧协议里可以当「有没有传坏」的指纹，但不能再当成防伪造的签名。新协议用 SHA-256 这一档，密码用专门的慢哈希。

3. **摘要一致是不是就说明包是服务器发的、也没人看过？** 只能说明内容和这份指纹相同。保密靠加密。是谁发的靠签名或可信通道给出指纹。包里自带一份 MD5 并自己和自己比，谁改包谁也能改那份 MD5。

4. **钥匙写在客户端常量里安全吗？** 安装包可以被打开。常量钥匙只能挡住不会翻包的人。真正的私钥不应进客户端。会话钥匙走 TLS 之后的安全下发，落盘用系统密钥库包裹。

5. **有签名为什么还能被重放？** 签名证明内容没改、是私钥持有者签的。整段再发一次，签名仍然有效。要有一次性 nonce 或时间窗，服务器拒绝见过的请求。

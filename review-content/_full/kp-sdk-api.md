## 一句话

先抓住对比：**你在写 App 时，自己拥有 `Application` 和整条启动链；写 SDK 时，你是住进别人进程里的房客。**

所以开场只记三句：

1. **时机不归你。** 宿主可能隐私同意后才 `init`，也可能子线程、也可能调两次。别把「我一定在 Application 里先跑完」写进假设。
2. **对外只留窄门。** 宿主看见的是 `init` / 进房 / 发送 / 回调和错误码；Socket、心跳、某家 RTC 都藏在门后。
3. **契约要写死。** 哪条线程回调、空不空、耗时是否异步——Java 宿主没有 Kotlin 空安全替你兜，写不清就会变成对方线上的崩溃。

Hilt、协程、具体网络栈都是门后的实现选择，**不要出现在对外签名上**。细节见下面「组成」和「原理」。

## 组成与结构

对外只留宿主真的要调用的面：

| 对外 | 对内 |
|------|------|
| `init(config)`、进房、发送、回调 | 连接、鉴权、心跳、存储可以分模块 |
| 错误码和状态枚举 | 重试、补拉、队列 |
| 线程约定写在方法注释里 | 想用协程就用在内部，挂起函数不要直接出现在 Java 宿主的 API 上 |
| 回调接口 | 具体 RTC、具体网络栈可替换 |

直播底座的边界是：对外是房间和信令，RTC 前面有适配层。业务只调进房、推拉流、回调。换一家 RTC，只换适配实现，回归集中在适配层。课件、白板不进这个 API。

IM SDK 的边界是：连接、消息、存储、推送协同。宿主不要碰到 Socket。发送状态（本地插入、发送中、Ack、失败）由 SDK 维护，宿主订阅结果。

质量面也是 API 的一部分：埋点、日志回捞、灰度开关。回捞要有开关、脱敏和体积上限。混淆 keep 随包给出，不要等宿主第一次发版才发现路由类或回调被裁掉。

## 原理（深度，分步骤，讲清为什么）

**1. 为什么初始化不能假设 Application 的时机**

App 自己可以在 Application 里按顺序初始化。SDK 被别人集成，对方可能在同意隐私政策之后才调用 `init`，也可能在子线程调用，甚至多次调用。所以 init 要幂等：第二次调用要么忽略，要么只更新允许变的配置。没 init 就调用业务方法，返回明确错误码，不要空指针。

SDK 也不要自己偷偷建 ContentProvider 做重初始化。那会跑在宿主启动早期的主线程上，对方的 ANR 和你的网络叠在一起，栈还在宿主进程里。

**2. 为什么耗时 API 不能是同步的**

宿主会在主线程调用。同步方法里一旦 DNS、建连、读数据库，ANR 就记在宿主头上。对外文档写明：哪些方法任意线程都可以，哪些必须在主线程（通常只有碰 View 的），回调回到哪条线程。耗时的一律异步，错误用错误码，不要抛受检异常让 Java 调用方到处 try。

回调线程要固定。有时在主线程，有时在 Socket 线程，宿主一更新界面就崩溃。内部切好再回调，比要求每个宿主都记得 post 更安全。如果提供「回调线程」配置，默认主线程，并在文档里写。

**3. 为什么不把 Hilt 或某个 JSON 库写进 API**

宿主可能用 Koin，可能用手动装配，也可能是纯 Java。API 上出现 Hilt 注解，对方就得引入你的依赖注入。JSON 库的异常类型如果出现在方法签名里，对方还得依赖那一个序列化库。对外用自己的数据类和错误码，内部爱用什么用什么。

手动装配对 SDK 更干净：`SDK.init(config)` 里自己 new 连接模块和存储模块。测试时可以提供 `init` 的测试配置替换实现。小 SDK 不必先上 Hilt。

**4. 适配层为什么要薄**

RTC、推送、甚至底层 Socket，各家的回调名字都不一样。如果业务直接调某一家的进房方法，换供应商等于改所有页面。适配层只留下进房、推拉流、静音、回调这几个词，把供应商的状态映射成自己的状态机。回归用例打在适配层上：同一组进房失败、断线、权限拒绝，换实现都要过。

适配层里不要堆业务。课件翻页不是 RTC 的职责。塞进去之后，换 RTC 要回归课件。

**5. 版本兼容和混淆**

SDK 一旦发出去，旧宿主会留很久。删方法、改参数顺序、改回调线程，都是不兼容。新能力加方法或加可选配置，旧方法留着并标上替代关系。数据类如果做了序列化，字段只能加不能改含义。

混淆会把回调接口、反射注册的类、JNI 方法名改掉。keep 规则跟 SDK 一起交付。多进程时要说明：连接在哪个进程，宿主的主进程回调是否跨进程。跨进程回调是 Binder，同样不能在里面做耗时操作。

**6. toB 定制为什么不能复制主干**

一家客户要一个特殊字段，就在主分支复制一套连接代码，下一家再复制，主干就死了。差异放配置和扩展点：能开关的不写死，能监听的用回调，协议字段按版本兼容。融云这条的说法是上千家客户，主干和定制分开。快传的插件则是宿主和插件的 API、资源要双向兼容，并生成 keep，避免误删。

公开方法先写线程和空值，再写功能。Java 宿主没有 Kotlin 的空安全，缺了空注解就会变成平台类型，调用方一调就可能空指针。回调固定抛回约定线程，不要有时在读线程、有时在主线程。init 幂等，没 init 就调用返回明确错误码。so 除了自己编的，RTC 和推理库带进来的也要看 16KB 对齐，否则宿主在新系统上加载失败。

删方法、改参数、改回调线程都是不兼容。新能力加重载或可选配置，旧方法留着转调。一家客户的差异放配置和扩展点，不要为这一家复制一条连接实现，否则修复合不回所有分支。

跨进程回调也是 Binder，里面同样不能做耗时操作，否则卡的是调用方线程。

错误用错误码，不把序列化库的异常类型抛给宿主。

第二次 init 要幂等，不能把连接再建出一条。

## 使用与实践

设计一个新 API 时按这个清单过一遍：Java 能调用吗？空注解有没有（Kotlin 调 Java 时没有注解会变成平台类型，运行时仍可能空指针）？会不会阻塞？回调在哪条线程？失败是错误码还是崩溃？第二次 init 会怎样？宿主没调 init 会怎样？混淆之后还能不能收到回调？

内部模块按连接、会话、收发、存储分开，便于替换和测试。对外只给一个入口类，避免宿主依赖内部包。内部包可以混淆得更狠，公开 API 保持名字稳定。

日志默认不包含 token 和消息正文。回捞由用户或宿主开关触发，体积有上限。灰度用配置，而不是为灰度再发一个分支包。

16KB 页对齐是现在 so 的交付问题：不只检查自己编的库，第三方 RTC、MNN、FFmpeg 带的 so 也要看 ELF 对齐。对不齐要升级 NDK 或对方 SDK，或在编译参数里按 16KB 对齐。这是打包兼容，不是业务 API，但会让宿主无法上架。

## 例子（至少 1 个完整代码或伪代码块 + 边界场景）

对外是同步返回「已接受」，结果走回调。init 幂等。错误码而不是异常：

```kotlin
object LiveSdk {
    @Volatile private var ready = false

    @JvmStatic
    fun init(config: Config): ErrorCode {
        if (ready) return ErrorCode.OK
        graph.start(config) // 内部装配，不要求宿主有 Hilt
        ready = true
        return ErrorCode.OK
    }

    @JvmStatic
    fun enter(roomId: String, cb: EnterCallback) {
        if (!ready) {
            cb.onResult(ErrorCode.NOT_INIT, null)
            return
        }
        engine.enter(roomId) { code, room ->
            main.post { cb.onResult(code, room) } // 固定回主线程
        }
    }
}

interface RtcAdapter {
    fun join(roomId: String, cb: (ErrorCode) -> Unit)
    fun leave()
}
```

边界一：`enter` 里直接 `socket.connect()` 并阻塞读认证结果。宿主在按钮点击里调用，5 秒后输入 ANR，栈在宿主主线程。应立即返回，结果由回调带错误码。

边界二：回调有时在读线程、有时在主线程。宿主第一次没崩，第二次更新 Compose 状态就抛错。SDK 内部统一 post 到约定线程。

边界三：为了方便，`init` 要求传入 `Hilt` 的 Application 组件。纯 Java 宿主和用 Koin 的宿主都接不了。改成普通 `Config` 对象，里面是密钥、日志开关和环境。

边界四：新版本把 `enter(roomId)` 改成 `enter(roomId, role)` 并删掉旧方法。线上旧宿主编译失败或运行找不到方法。新能力应加重载，旧方法转调新方法并给默认 role。

## 画面（text 结构图）

```text
宿主 App
  │  init(config) / enter / send
  │  只看见错误码和回调（线程有约定）
  ▼
SDK 公开 API
  ├─ 房间 / 消息状态机
  ├─ 连接 · 鉴权 · 心跳 · 存储     内部模块
  └─ 适配层 → 具体 RTC / 推送 / Socket
                 换实现不改公开 API

不做的事
  不强制 Hilt
  不在 API 上暴露挂起函数给 Java 宿主
  不在同步方法里做网络
  不把课件、某一家客户的分支写进主干

交付一起给
  keep 规则、线程说明、错误码表、so 的 16KB 对齐
```

## 常见坑与追问（至少 3 条）

1. **为什么 SDK 不直接用宿主的 Hilt？** 宿主不一定用 Hilt，也不一定在 Application 里允许你安装模块。对外用 `init(config)` 手动装配，内部可以自己用任何方式创建对象。强制依赖注入框架会把接不了的宿主挡在外面。

2. **同步方法里查一次本地数据库，应该没问题？** 主线程上的数据库仍可能被锁住或做较重的 IO，这是 ANR 的常见栈。对外要么保证纯内存且无锁，要么改成异步。文档要写线程，不能靠「一般很快」。

3. **适配层会不会变成大而全的第二次业务层？** 会，如果把课件、白板、某个客户的逻辑放进去。适配层只翻译进房、媒体和回调。业务模块放在 SDK 外面或独立模块里，通过窄接口使用房间能力。

4. **Kotlin 的可空类型对 Java 宿主够不够？** Java 没有这套类型。公开 API 要加空注解，Java 实现的回调在 Kotlin 侧按可空处理。否则平台类型看起来像非空，运行时仍会空指针。

5. **一家客户要改协议，为什么不能开分支？** 分支会在下一次主干修复时漏掉这家客户，或者每次修复都要合很多次。差异放配置和扩展点，主干保持一条。插件和宿主之间用兼容检测和 keep，而不是各改各的内部类。

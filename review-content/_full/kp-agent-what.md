## 一句话

聊天模型只根据这一句往下说；Agent 多一个循环：看当前情况、调用工具、把结果放回上下文、再决定，直到给出结论或停下来等人确认。

## 组成与结构

画板就四块，够面试讲清楚，不必装成模型训练。

| 块 | 干什么 | 线上排查 Agent 里是什么 |
|----|--------|-------------------------|
| 模型 | 推理、写结论 | 看日志和代码，给出可能原因 |
| 工具 | 真正做事 | 拉日志、在仓库里定位类和调用链 |
| 上下文 | 这一轮能看见的材料 | 现象、日志片段、相关源码、输出格式 |
| 停机条件 | 什么时候不许再自动往下 | 给出初步分析后必须人确认，不直接改线上 |

旁边四个词各记一句：

- RAG：先检索再回答。按问题去捞日志和源码，不是把整个仓库塞进提示词。
- 记忆：跨轮还留着的信息。一次排查里的日志路径、已经看过的类，算短期记忆。
- ReAct：先想一步，做一步，看结果再想。就是上面的循环，不是另一个产品。
- 评测：拿一批真实 case 对答案。80%～90% 来自抽样，不是线上每一单都自动判对。

主流产品的差别不在「谁更聪明」，在跑在哪、能不能动仓库、工具谁提供、错了谁负责。

| 产品 | 跑在哪 | 适合怎么说 |
|------|--------|------------|
| Cursor Agent | IDE | 日常改当前仓库，看 diff，跟项目规则走 |
| Claude Code | 终端 | 跨很多文件，自己跑构建和测试 |
| GitHub Copilot | IDE 补全，也有 Agent | 行内补全、和 issue / PR 连着，知道即可 |
| 云端代理 | 远程机器 | 没在生产用过就直说 |
| Dify / Coze | 搭流程的后台 | 业务工作流，不是用来改 Android 工程 |
| LangGraph / 自研编排 | 代码 | 步骤固定、要分支和人工卡点 |

客户端面试里的一句：排查用固定工作流，因为步骤清楚、要验收；写业务代码用 IDE Agent，因为改动要落在 diff 里被人看。

## 原理

1. **循环比单次补全多了反馈。** 补全模型看到光标附近的代码，猜下一小段。Agent 可以先搜索，发现方向错了再搜一次，把工具的输出当新事实。没有这个回路，它只能在第一眼的上下文里编完。
2. **工具调用是结构化动作。** 模型产出的不是直接改用户磁盘的魔法，而是「调用哪个工具、参数是什么」。运行时执行工具，把 stdout、文件片段、错误码塞回对话。下一步推理能看见上一步的真实结果。权限边界就设在工具上：只给读日志的接口，它就改不了线上配置。
3. **上下文是有限的。** 窗口装不下整个仓库和三天日志。所以要先检索：用房间号、用户、时间把日志裁小，用报错和类名把源码裁小。这就是 RAG 在这个项目里的具体意思。裁错了，模型会在错误的文件上给出很完整的错误结论。
4. **停机条件决定能不能上线。** 没有停机，循环会一直改、一直调。排查 Agent 的停机是「写出初步原因和对应代码位置后交给人」。人不确认，不改代码、不发版。写代码的 Agent 停机是「diff 出来了，测试命令跑完了」，人再决定提交。
5. **多智能体不是默认更强。** 一个规划、一个写码、一个审查，听起来完整，步骤固定时它们会把同一段上下文来回传，更贵也更难验收。排查这种步骤清楚的事，一条流水线比多个角色互相对话更稳。
6. **数字口径。** 正确率是抽样：抽一批已经有结论的问题，看初判是否指向同一原因。耗时下降省的是人肉翻日志、对源码的时间，确认和改代码仍算人的时间。不能说成「线上 90% 的 bug 被它修好」。

## 使用与实践

讲自己的排查流时按这个顺序，不跳到框架名词：

```text
现象 / 反馈
  -> 按房间、用户、时间把日志拉下来
  -> 用报错、类名、信令把相关源码找出来
  -> 模型给出可能原因、对应代码、建议先看哪
  -> 人确认，再决定改不改
```

主动说边界：它做取证和初判，不是自动发版。日志有隐私，范围、脱敏、谁能看，被问到要有一句。

写业务代码时，人定范围和验收，Agent 起草，人看 diff。协议、权限、混淆 keep、线上开关，它只能拟草稿。

## 例子

一次工具循环可以压缩成下面这种口述，不必展示真实日志：

```text
目标：解释房间 1001 在 21:03 没有收到信令
1. 调日志工具，参数是房间、用户、时间窗 -> 返回 40 行
2. 看到超时在 SocketRead，于是搜仓库里的读超时
3. 读到重连退避和心跳间隔
4. 输出：先看心跳是否在主线程被堵住；不改代码
```

若第 2 步搜到的类不是当前进程的，人在确认时否掉，这就是停机条件在起作用。评测时把这种 case 放进样本，看初判是否和事后结论一致。

## 画面

```text
目标
  -> 模型决定下一步
  -> 工具（日志 / 搜索 / 读文件 / 跑命令）
  -> 结果放回上下文
  -> 再决定
  -> 结论或等人确认

四块：模型、工具、上下文、停机条件
```

## 常见坑与追问

1. **把 Agent 说成更大的聊天模型。** 追问：多出来的循环是什么？自己调工具并把结果放回去，直到停机。
2. **80%～90% 被问成线上自动修复率。** 追问：样本是什么？已经有人结论的一批问题，比的是初判是否同因。耗时省的是翻日志，不是省掉人的确认。
3. **为什么排查不用多个自由对话的智能体？** 追问：步骤固定时怎样更稳？一条流水线，每步有输入输出，方便验收，也比角色之间互聊省。
4. **云端代理和 IDE Agent 哪个能改你的仓库？** 追问：责任在哪？IDE 里改动能看 diff，人提交；云端没在生产用过就不要讲成已落地。

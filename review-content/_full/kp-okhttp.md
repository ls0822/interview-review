## 一句话

OkHttp 把一次 HTTP 调用做成拦截器链，链上负责重试、补头、缓存、取连接和真正读写。连接池按地址复用已经建好的 TCP，避免每次请求都握手。它是短请求的事实标准，和自研 IM 长连接不是同一条连接。

## 组成与结构

一次 `Call` 从应用拦截器走进去，再从同一段栈退出来。材料里的顺序是：

```text
应用拦截器
  → 重试 / 重定向
    → Bridge（补齐 HTTP 头、透明压缩）
      → Cache
        → Connect（从连接池取或新建连接）
          → 网络拦截器
            → CallServer（真正写请求、读响应）
```

越靠外的拦截器越早看到原始请求、越晚看到最终响应。网络拦截器夹在「已经拿到连接」和「真正读写」之间，能看到每一次真实的网络往返。

超时分四类，不要合成一个数：`call` 是整次调用的上限，`connect` 是建连，`read` 是等待下一段响应字节，`write` 是写出请求。连接池、HTTP/2、证书、代理、事件监听都是客户端级配置，所有 Call 共享。

Retrofit 坐在 OkHttp 上面：接口方法上的注解描述路径和参数，转换器负责 JSON。真正的连接、重试和 TLS 仍是 OkHttp。

## 原理（深度，分步骤，讲清为什么）

**1. 为什么用链而不是一个大方法**

重试、缓存、加头、建连、读写，每件事情都会失败，而且顺序不能乱。写成拦截器之后，每一环只决定两件事：要不要改请求、要不要调用 `chain.proceed`。调用 proceed 就是把控制权交给下一环。返回时响应再沿原路改回来。业务想打日志、加公共参数，就插入自己的拦截器，而不必改库。

应用拦截器和网络拦截器的差别是位置。应用拦截器在重试和重定向之外：一次 `Call` 里，你加上去的应用拦截器通常把整个过程看成一次 proceed，里面发生了几次重定向它默认看不到。网络拦截器在 Connect 之后：每一次真正发到网络上的请求都会经过它，包括重定向后的那一次。所以「统计真实网络耗时、看最终发出去的 URL」放网络拦截器；「加 token、打业务日志、短路径缓存」放应用拦截器。

**2. 每一环为什么按这个顺序**

重试和重定向放最外（仅次于应用拦截器），是因为失败后要重新走缓存判断和建连。如果重试包在 CallServer 里面，就会把一次已经坏掉的连接反复用下去。

Bridge 补上 Host、Content-Type、User-Agent，并在双方都支持时加上压缩标记。这一步要在缓存之前：缓存键和缓存内容依赖最终的头。透明 GZIP 是说应用拿到的响应体已经解压，不必自己再解，除非你故意拿原始字节。

Cache 在 Connect 之前，是为了命中时根本不要连接。缓存新鲜就直接返回；需要校验时才继续往下，带上条件请求头，下一环连上服务器问「有没有变」。

Connect 从连接池找一条能用的连接：地址、代理、证书这些条件匹配，并且空闲没有超过保活时间。找不到才做 DNS、TCP、TLS。HTTP/2 还要在这条连接上开流。找到或建好之后，连接交给后面的环，环结束时连接回到池里，而不是立刻关掉。

CallServer 把请求头和请求体写进连接，再把响应读出来。它是唯一真正碰 Socket 读写的一环。

**3. 连接池为什么能省时间**

TCP 握手加 TLS 往往比一次小接口的业务数据更贵。同一个目标（主机、端口、代理）上一条已经完成握手的连接，下一个请求可以直接用。HTTP/1.1 靠多条连接并行，因为一条连接一次只能跑一个响应。HTTP/2 在一条 TCP 上开多个流，并行不再等于多条连接，但丢包时仍有 TCP 队头阻塞。池的空闲连接会在保活时间到了之后关掉，避免占着服务器的文件描述符。

池是进程内、这个 OkHttpClient 内共享的。新 `new OkHttpClient()` 就是新池。全局应共享一个配置好的客户端，而不是每个请求新客户端。

**4. 重试会重复什么**

幂等的 GET 失败了可以再走一遍链。POST 默认不能盲目重试：请求体可能已经送到服务器并执行了，只是响应没回来。重定向会换 URL 再走。应用如果在拦截器里自己 `proceed` 两次，等于自己做了重试，服务器会看到两次。上传和支付不要假设库会帮你只执行一次。

**5. 事件监听和拦截器各看什么**

拦截器能改请求和响应，适合加头、校验、缓存策略。事件监听不改数据，只通知「开始 DNS、连接获得、响应头到了」。耗时分段打点用监听更合适，避免为了打点去改链。证书和代理配在客户端上，影响 Connect 那一环如何建连。

四个超时要一起看。call 是整次调用的上限，比连接超时还短时，连接超时永远不会先触发。上传把写超时单独放宽，不要把 call 设成无限。全局共享一个客户端，不同业务用 newBuilder 派生超时，连接池仍然是同一份。非幂等请求不要交给默认重试，用幂等键或先查询再决定是否重做。

看最终 URL 和每一次重定向用网络拦截器，加 token 用应用拦截器。每个请求都 new 一个客户端，连接池就是空的，弱网上时间会花在反复握手。

## 使用与实践

全局一个 `OkHttpClient`，共享连接池和线程。按业务克隆出带不同超时的客户端时，用 `newBuilder()`，池可以继续共享。每个请求 `new OkHttpClient()` 会让连接永远复用不上。

公共 Header、登录态放应用拦截器。证书锁定、要观察每一次重定向的日志放网络拦截器。缓存只用于允许缓存的 GET，带用户隐私的响应不要进共享缓存。

超时按接口性质分：配置拉取可以较短；上传大文件要把写超时放宽，并用进度，而不是把 call 超时设成无限。失败要映射成业务错误码，不要把 OkHttp 的异常原文抛给 UI。

自研长连接如果是单独的 Socket，心跳断了不会由这个连接池自动恢复。短请求的池和 IM 的长连接分开监控：一个看接口成功率和分位耗时，一个看在线率和重连次数。

Retrofit 的接口只声明路径和模型。JSON 库选一种固定下来。SDK 不要把转换库的异常类型直接抛给宿主。

## 例子（至少 1 个完整代码或伪代码块 + 边界场景）

共享客户端，应用拦截器加 token，网络拦截器只记录真正发出去的 URL：

```kotlin
val http = OkHttpClient.Builder()
    .connectTimeout(5, TimeUnit.SECONDS)
    .readTimeout(10, TimeUnit.SECONDS)
    .writeTimeout(10, TimeUnit.SECONDS)
    .callTimeout(20, TimeUnit.SECONDS)
    .addInterceptor { chain ->
        val req = chain.request().newBuilder()
            .header("Authorization", tokenStore.get())
            .build()
        chain.proceed(req) // 一次调用包住内部的重试和重定向
    }
    .addNetworkInterceptor { chain ->
        val req = chain.request()
        metrics.onRealRequest(req.url) // 重定向后的每个 URL 都会到这里
        chain.proceed(req)
    }
    .build()

val retrofit = Retrofit.Builder()
    .baseUrl("https://api.example.com/")
    .client(http)
    .addConverterFactory(JsonConverterFactory.create())
    .build()
```

边界一：在应用拦截器里看到的 URL 一直是原始地址，抓包却是重定向之后的 CDN 地址。这是位置决定的。要看最终 URL，把日志挪到网络拦截器或事件监听的连接阶段。

边界二：每个页面 `OkHttpClient.Builder().build()`。池是空的，每个图片和接口都重新握手，弱网上接口时间里一大半是 TLS。改成进程内共享。

边界三：POST 创建订单，读超时后库或业务又自动重试。服务器已经创建成功，客户端再创建一次。创建类接口用幂等键，并禁止无条件重试；超时后先查询订单是否存在。

边界四：call 超时 20 秒，连接超时 30 秒。整次调用会先被 call 超时打断，连接超时永远不起作用。四个时间要放在一起看，call 应覆盖你允许的总等待。

## 画面（text 结构图）

```text
Call.enqueue / execute
        │
        ▼
 应用拦截器          加 token、业务日志（把重试看成一次）
        │
 重试和重定向        失败或 3xx 时整段重走下面的链
        │
 Bridge              补头、声明压缩
        │
 Cache               新鲜则直接返回，不建连
        │
 Connect             连接池：有空闲且匹配就复用，否则 DNS+TCP+TLS
        │
 网络拦截器          看见每一次真实请求
        │
 CallServer          写请求、读响应
        │
        ▼
 响应沿原路返回；连接归还连接池

HTTP/1.1：一个连接同时一个响应，并行靠多连接
HTTP/2  ：一个连接多个流
自研 IM Socket 不在这个池里
```

## 常见坑与追问（至少 3 条）

1. **应用拦截器和网络拦截器有什么差别？** 应用拦截器在重试之外，一次 proceed 覆盖整个调用。网络拦截器在拿到连接之后、真正读写之前，每次真实网络请求都会经过，包括重定向之后的请求。改公共头放外面，看最终 URL 和连接上的字节放里面。

2. **为什么全局只能共享一个客户端？** 连接池、线程和证书配置挂在客户端上。每次新建客户端就是空池，TLS 无法复用。需要不同超时时用 `newBuilder()` 派生，而不是从零再建一个池。

3. **连接池复用了，是不是就等于长连接 IM？** 不是。池复用的是到同一 HTTP 主机的短请求连接，请求结束连接回到池里等待下一个 Call。IM 是一条有鉴权、心跳和业务 Ack 的会话，通常是单独的 Socket。两条都断的时候要分开重连。

4. **开启缓存之后用户看到了别人的数据？** 缓存键如果忽略了身份，同一 URL 的私有响应会被下一个用户命中。带登录态的接口默认不要走共享 HTTP 缓存，或者把身份放进缓存键并由服务端给出明确的缓存头。

5. **重试为什么让订单重复？** 请求已经执行、响应在路上丢了，客户端看起来像失败。非幂等请求不能无脑重试。要幂等键，超时后先查结果。GET 和明确声明可重试的接口才交给重试环。

## 一句话

客户端网络优化就三件事：少发、早点连上、每次少传一点；弱网时别用蛮力重试，把失败分成可重试和必须降级。成绩看成功率、耗时分位和错误码，不看「感觉快了」。上传分片和离线包差分是这套话术的两个落点。

## 组成与结构

| 方向 | 手段 | 在项目里长什么样 |
|------|------|------------------|
| 减少请求 | 合并、缓存、差量、只拉变更 | 离线包差分，而不是每次全量；接口能用缓存就不打 |
| 更快建连 | 预连接、DNS 优化、HTTP/2 或 QUIC、连接复用 | 共享 OkHttp 连接池；HTTPDNS；能走 HTTP/2 就不为每个请求新握手 |
| 更少字节 | 压缩、WebP、差量包、采样上传 | 图片不要原图直出；上传不必把无关字段全传 |
| 弱网 | 超时分开设、退避重试、断点续传、优先级队列 | 大文件分片；失败换策略而不是立刻再来十次 |
| 体验 | 并行分片、预加载、占位 | 上传并发有上限；进房时资源和房间并行，界面先出占位 |
| 监控 | 成功率、分位耗时、错误码、网络类型 | 离线包 3 日成功率、上传按文件大小分层 |

这六行是清单。面试时不要平铺，挑一条链路从头讲到指标。例如上传：队列 → 分片并发 → 校验 → 失败续传 → 小文件和大文件的成功率变化。例如离线包：差分 → 校验 → 失败回滚 → 3 日成功率。

弱网测试用工具限速、丢包、加延迟，而不是只在办公室 Wi-Fi 上看。心跳不要一弱网就改成很密。

## 原理（深度，分步骤，讲清为什么）

**1. 一次请求的时间花在哪**

大致是 DNS、TCP、TLS、发送请求、等首字节、下载正文。小接口往往建连比正文贵，所以复用连接、预连接、少发请求，比把 JSON 再压缩 10% 更有效。大文件相反，正文传输占大头，该做的是压缩、差分、并行分片和断点，而不是再优化一次握手。

先看分位而不是平均值。平均值会被少数失败拉高或被大量缓存命中拉低。P50 和 P99 分开：P50 差多半是路径设计问题，P99 差多半是弱网、重试和超时把尾巴拖长。

**2. 为什么「少发」优先于「发得更快」**

没发出去的请求没有 DNS、没有握手、也不会失败。合并是把同一时刻的多个小请求合成一个，省掉重复的头和握手。缓存是短时间里结果不会变，连发都不要发。差量是两边都有上一版，只传变化。只拉变更是客户端带上版本或序号，服务器没有新数据就返回空。

离线包如果每次全量下载，包一大，失败率和流量一起变差。差分的前提是本地有完整旧版，能把补丁打上去。没有旧版或补丁失败，要能退回全量，不能卡死。

**3. 建连优化为什么会互相打架**

预连接占用 Socket 和服务器连接数，预错域名就是浪费。连接池复用要求主机、端口、代理一致，换了一个 CDN 域名就用不上原来的池。HTTP/2 多路复用减少连接条数，但 TCP 丢包仍会堵住同一连接上的流；QUIC 可以减轻这件事，前提是 UDP 能通，不通就要退回。DNS 优化若把 URL 换成 IP 却不处理证书，会从「慢」变成「全部失败」，失败比慢更差。

**4. 弱网重试为什么会让情况更糟**

超时后再立刻重试，网络上同时有旧请求和新请求，拥塞更重，服务器还可能把非幂等请求执行两次。正确的重试是：只重试可能成功的那一类错误（连接被重置、短暂 5xx），不重试 4xx 业务拒绝和证书错误；间隔指数退避；有次数上限；非幂等请求带幂等键或先查询再决定是否重做。

断点续传依赖服务器支持范围请求或分片序号。客户端记下已经确认的偏移，失败后从偏移继续，而不是从 0 再传。并行分片要有上限，并发开到几十，在弱网上只是互相抢带宽，每个分片都超时。

优先级队列保证小的、用户正在等的配置请求不被一个后台大包堵死。公平是说低优先级最终仍会执行，而不是永远让路。多业务上传共用一条队列时，要有权重，避免一个业务把池占满。

**5. 指标为什么要分层**

「成功率 99%」如果不说分母，就没法优化。离线包材料里的口径是 3 日成功率 99.4%，插件包另一档是 99.9%，H5 使用率提升要单独说。上传是小文件大约提升 8 个点、大文件大约 15 个点，两个数不能合成一个。进房 99% 和小学含动态下载的 95% 也不是同一个口径。

分层维度至少有：网络类型、端版本、文件大小或包类型、错误码。错误码要能区分 DNS、超时、TLS、HTTP 状态、校验失败。都叫「网络错误」就不知道该改 DNS 还是该改校验。

**6. 体验优化不能牺牲正确性**

预加载和占位让界面先动起来，但失败要能收回占位，不能把没下载完的包当成已安装。并行是为了填满带宽，不是为了把同一份工作做两遍。采样上传是少传字节，采样率要保证还能排查问题，不能把失败现场也采样没了。

## 使用与实践

做之前先有分段耗时和错误码。没有基线就不要同时改差分、并发和超时，否则不知道是哪一个带来的变化。

上传链路：有界队列、按业务权重调度、分片并发度设上限、每片和整文件校验、失败续传、结果按大小分层统计。并发度用实验定，不拍脑袋开到 CPU 核数的很多倍。

离线包链路：能差分就差分，下载完校验，校验失败删除，替换采用可回滚的方式，过期 URL 重新签发而不是重试。Push 预处理是在用户打开之前就把包拉到本地，打开时少等一次。预处理失败不能影响打开后的正常下载。

进房链路：房间连接和资源下载能并行就并行，但进房成功的定义里如果包含「资源可用」，就要把资源超时单独算进那 95% 的口径，不要和纯进房的 99% 比。

弱网用工具模拟高延迟、丢包和带宽上限，看的是成功率有没有崩、重试有没有打满，而不是动画顺不顺。心跳保持原策略，除非数据说明探测太慢导致长时间假在线。

## 例子（至少 1 个完整代码或伪代码块 + 边界场景）

上传队列把并发限制住，失败按错误类型决定续传还是停：

```kotlin
class UploadQueue(private val parallel: Int) {
    private val running = ArrayDeque<Job>()

    suspend fun enqueue(task: Upload) {
        if (running.size >= parallel) waitSlot()
        running += scope.launch {
            var offset = task.confirmedOffset()
            while (offset < task.size) {
                when (val r = task.putPart(offset)) {
                    is Ok -> offset = r.next
                    is Timeout -> delay(task.backoff())      // 续传，不从 0 开始
                    is Rejected -> { task.fail(r.code); return@launch } // 4xx 不重试
                }
            }
            task.finishIfChecksumMatch()
        }
    }
}
```

离线包先看本地能不能打差分，不行再全量，成功才替换：

```kotlin
suspend fun update(pkg: Package) {
    val file = if (local.has(pkg.base)) download(pkg.patch) else download(pkg.full)
    if (!file.sha256Equals(pkg.digest)) {
        file.delete()
        return
    }
    local.applyAtomically(file) // 失败则继续用旧版本
}
```

边界一：大文件并发开到 16，在限速 100KB/s 的弱网上每片都超时，成功率下降。并发度要随网络类型降，例如蜂窝网只用 2。监控若只看 Wi-Fi，这个问题不会出现。

边界二：差分补丁下载成功但本地旧包已经被清理。硬打补丁会得到坏目录。打补丁前确认基线版本，不符合就改下全量。

边界三：非幂等的「创建」接口超时后自动重试三次。服务器创建了三单。这类请求不进自动重试，或带同一个幂等键。

边界四：把含动态下载的进房和纯房间进房放进同一个成功率。优化资源下载之后数字变了，却说不清是房间连接变好了还是下载变好了。口径分开报。

## 画面（text 结构图）

```text
一次调用的时间
  DNS → TCP → TLS → 请求 → 首字节 → 正文
  小接口：前三段往往更贵 → 复用、预连接、少发
  大文件：正文更贵 → 压缩、差分、分片、断点

优化清单
  少发    合并 / 缓存 / 差量 / 只拉变更
  快连    预连接 / HTTPDNS / HTTP2·QUIC / 连接池
  少字节  压缩 / WebP / 差分 / 采样
  弱网    分超时 / 退避 / 断点 / 优先级
  体验    有限并行 / 预加载 / 占位
  监控    成功率 · 分位 · 错误码 · 网络类型

重试
  连接重置、短暂 5xx → 退避后再试，有上限
  4xx、证书错误、校验失败 → 不按原请求硬重试
```

## 常见坑与追问（至少 3 条）

1. **为什么不先把所有接口的超时都加大？** 加大超时让失败更晚才暴露，队列里堵着的慢请求更多，P99 更差。超时应按接口分开，该失败的失败，再按错误类型决定是否退避重试。

2. **并发越高越快吗？** 带宽够、服务器允许时，有限并发能把大文件打满。弱网和很小的文件上，并发只增加握手和超时。上传要按文件大小和网络分层，并发度要有实验，而不是固定一个很大的数。

3. **差分一定比全量好吗？** 本地有正确的旧版本时，差分省流量、也少传字节。没有基线、补丁失败或补丁比全量大时，应走全量。替换必须可回滚，不能留下半个新包。

4. **成功率从 90 到 99 说明优化生效了吗？** 要看分母。3 日离线包、插件包、小文件、大文件、含动态下载的进房，是不同口径。还要看错误码有没有从超时变成校验失败，那种「更快但更错」不算成功。

5. **预连接和预解析有什么副作用？** 它们把成本挪到点击之前，也会占用连接和电量。预错主机、预太多，正式请求到来时该用的连接反而被挤掉。只对马上要用的域名做，并和连接池共享同一个客户端。

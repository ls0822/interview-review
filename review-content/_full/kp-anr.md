## 一句话

系统认为主线程没有按时处理完它该处理的事，就记一次 ANR，并抓当时各线程的栈。排查不是先猜业务，而是先看主线程栈停在自己的重活、等锁，还是卡在 Binder。输入 ANR 还要考虑：队列前面有一条慢消息，点击根本轮不到。

## 组成与结构

时限随版本变化，面试说大约值，并声明「不同版本会变」：

| 类型 | 大约时限 | 为什么容易碰到 |
|------|----------|----------------|
| 输入（点击、按键） | 5 秒还没处理完 | 主线程被慢消息堵住，或处理触摸的函数本身很重 |
| 前台广播 | 10 秒左右 | `onReceive` 里做了网络或磁盘 |
| 后台广播 | 60 秒左右 | 同样不能当后台线程用 |
| 前台 Service | 20 秒左右 | `onStartCommand` / `startForeground` 前的耗时 |
| ContentProvider | 10 秒左右 | 它可能在启动路径上，`onCreate` 里做重活会拖启动 |

发生时系统写出 `traces.txt`（或调试器里的线程栈），里面有主线程和其它线程的调用栈。ANR 对话框或系统日志只说明「超时了」，原因在栈里。

和掉帧不是同一个阈值。掉帧是一帧十几毫秒没画完，用户感到卡。ANR 是秒级没处理完输入、广播或服务。卡顿样例会发展成 ANR，但 16 毫秒的问题和 5 秒的问题排查粒度不同。

## 原理（深度，分步骤，讲清为什么）

**1. 为什么总是主线程**

输入事件、广播、服务的生命周期回调，默认投到主线程的 MessageQueue。主线程一次只处理一条消息。这条消息不返回，后面的点击、绘制、`startForeground` 都在等。系统侧有计时：输入分发下去太久没完成、广播或服务的主线程回调太久没返回，就判定 ANR，并给所有线程抓栈。抓栈是为了看到「现在卡住时大家都在干什么」，不只有主线程。

**2. 看栈的三种形态**

从上往下认主线程：

1. 栈在自己的业务函数里，例如 `parseJson`、`decodeBitmap`、`database.query`。就是主线程干了重活。这条最好修：把工作挪到 IO 线程，主线程只收结果。
2. 栈在 `monitor contention` 或等 `ReentrantLock`。主线程想拿一把被工作线程占着的锁，对方还在 IO 里。主线程自己的业务函数很短，时间耗在等锁。要看持锁的那条线程在干什么，而不是只看主线程最上面一帧。
3. 栈停在 Binder 的 `transact`。主线程在等另一个进程返回。对方可能是系统服务，也可能是自己的推送进程、WebView、SDK 进程。本进程栈已经说明不了对方为什么慢，要到对方进程的栈或服务端日志里看。

**3. 输入 ANR 为什么栈可能已经不在慢消息里**

点击也是一条消息。它前面如果排着一条解析大 JSON 的消息，点击要等那条走完。等用户感觉到卡、系统抓栈时，慢消息可能刚好执行完，主线程栈已经停在别的地方，甚至看起来很空。所以输入 ANR 要结合「抓栈前主线程刚刚执行完什么」。Trace、Perfetto 上主线程的时间片比一张瞬时栈更有用。原则仍是：主线程只做调度和轻量 UI。网络、磁盘、解码、大 JSON 离开主线程。

**4. 广播和 Provider 为什么特别亏**

`onReceive` 跑在主线程，而且广播超时是系统直接记 ANR，不会等你自己发现卡顿。在里面做网络，前台大约 10 秒就会爆。ContentProvider 的 `onCreate` 更早，启动时每个库都在这里初始化，主线程时间是加在一起的。启动路径上的 ANR 经常不是某一个业务页面，而是一串初始化。

**5. 前台服务的 ANR 和后台限制是连着的**

`startForegroundService` 之后必须很快 `startForeground`。服务主线程如果先做同步网络再挂通知，会先撞上前台服务的时限。这不是「通知渠道没配对」那么简单，是主线程没按时完成系统要求的那次回调。

**6. SDK 同步 API 为什么会变成宿主的 ANR**

调用方在主线程调用 SDK 的同步方法，方法里如果碰网络、磁盘或跨进程，栈在宿主主线程。崩溃和 ANR 记在宿主头上，不在 SDK 进程里。所以对外 API 要写明允许的线程；耗时的做成异步，回调再说明回到哪条线程。不要让宿主猜。

**7. 瞬时栈与 trace 怎么一起用**

输入 ANR 抓栈时慢消息可能刚跑完，主线程停在 `nativePollOnce`，栈像「没事」。要把点击分发时刻与此前数秒的主线程切片对齐（Perfetto / systrace），才能对上解析、锁或 Binder。看锁 ANR 时把持锁线程与主线程等锁帧配对，才能确定临界区里是否做了 IO。

## 使用与实践

开发期用 StrictMode 抓主线程磁盘和网络，问题在进线上之前就会响。线上看自己的耗时分位和错误码，ANR 率要和版本、机型、主线程最忙的页面放在一起看。单次排查用 traces 加 Perfetto：先分类是重活、锁还是 Binder，再决定看业务代码、持锁线程还是另一个进程。

修复顺序：先把主线程上的 IO 挪走；再缩短锁的范围，不在持锁时做 IO；最后才是跨进程调用改成异步。不要先加线程池而不看是不是锁等待，池子更多只会让锁更挤。

SDK 和中台代码默认不在主线程做网络。文档里写「此方法可在任意线程 / 必须在主线程 / 回调在主线程」。同步方法如果内部可能阻塞，就不要提供给 UI 线程调用。

## 例子（至少 1 个完整代码或伪代码块 + 边界场景）

主线程只收结果，解析放在 IO。这是「栈在 parseJson」这一类的改法：

```kotlin
fun renderFeed(raw: String, scope: CoroutineScope, sink: (Feed) -> Unit) {
    scope.launch(Dispatchers.Main) {
        val feed = withContext(Dispatchers.IO) { parseFeed(raw) }
        sink(feed) // 主线程只做这一次轻量赋值
    }
}
```

锁不要包住 IO。下面这种写法主线程一调用 `get()` 就会等在锁上，而工作线程还在锁里读盘：

```kotlin
private val lock = Any()

fun loadBlocking(): String = synchronized(lock) {
    File(path).readText() // 持锁做磁盘，谁调用谁被卡住
}

// 改成：锁只保护内存快照，磁盘在锁外
fun load(): String {
    val cached = synchronized(lock) { memoryCache }
    if (cached != null) return cached
    val fresh = File(path).readText()
    synchronized(lock) { memoryCache = fresh }
    return fresh
}
```

边界一：点击 ANR，主线程栈停在 `android.os.MessageQueue.nativePollOnce`，看起来在空等。说明抓栈时主线程已经空了，慢消息刚刚执行完。要看 trace 里点击被分发之前那一段主线程在跑什么，而不是认定「主线程没做事所以不是我们的问题」。

边界二：主线程栈在 `BinderProxy.transact`。本进程没有 `parseJson`。去看被调用进程的主线程或线程池是不是也堵了。自己的推送进程如果在 Binder 方法里做数据库，宿主主线程会一起等。

边界三：广播 `onReceive` 里启动协程但方法立刻返回，ANR 不会因为「开了协程」就消失——如果协程是 `runBlocking` 包着网络，主线程仍被堵住。`onReceive` 里只能做投递，不能阻塞等结果。

边界四：SDK 提供 `connect()` 同步连到服务器。宿主在 Application 或按钮点击里调用，ANR 栈全在宿主。应改成异步连接，错误用错误码回调，并写明回调线程。

## 画面（text 结构图）

```text
主线程 MessageQueue
  [慢消息 parseJson / 持锁 IO / Binder transact] [点击] [绘制]
        │
        └─ 点击等了大约 5 秒仍未处理完 → 系统抓全线程栈 → ANR

看主线程栈：
  业务函数 parseJson / query / decode   → 主线程重活
  monitor contention / ReentrantLock     → 等别的线程的锁（去看持锁者）
  Binder.transact                        → 等另一个进程
  nativePollOnce 且刚刚有慢消息          → 慢消息已经走完，要看 trace 时间线

SDK：
  宿主主线程 ──同步调用──▶ SDK 网络/磁盘  → ANR 记在宿主
```

## 常见坑与追问（至少 3 条）

1. **栈已经不在业务函数里，就能说不是 ANR 根因吗？** 不能。输入超时看的是点击有没有被及时处理完。前面的慢消息执行完之后，栈可能已经在等下一条消息。要用 trace 看超时前的主线程时间线。

2. **主线程在等锁，把锁去掉就好了吗？** 先看持锁线程在锁里做什么。如果锁里有磁盘或网络，应把 IO 移出临界区。如果只是临界区太长，再缩小锁范围。主线程尽量不要和 IO 线程共用一把大锁。

3. **Binder 栈为什么本进程日志看不出原因？** `transact` 表示在等对方进程。对方可能是系统服务，也可能是自己的子进程。要抓对方的栈，或看对方是否在 Binder 线程里做了数据库。跨进程接口不要做同步重活。

4. **前台服务 ANR 是不是通知没弹出来？** 常见是 `startForeground` 调用得太晚，主线程先去做别的了。通知要在服务起来后立刻挂上，类型还要和清单一致。网络放在挂上通知之后，并且不要阻塞主线程。

5. **为什么强调 SDK 的同步 API？** 宿主会在主线程调用你以为「只是读一下」的方法。方法里一旦碰到网络、数据库或跨进程，ANR 记在宿主。对外写明线程，耗时的做成异步和错误码。这和直播底座、IM SDK 的对外接口是同一条约束。

## 一句话

图片库负责异步加载、跟生命周期取消、内存和磁盘两级缓存、按目标尺寸采样解码，以及把同一张图的重复请求合成一次。Glide 在存量项目里最多，Coil 在新的 Kotlin 项目里常见。极大图和复杂 GIF 才会评估 Fresco。

## 组成与结构

| 维度 | Glide | Coil | Picasso | Fresco |
|------|-------|------|---------|--------|
| 语言和风格 | Java / Kotlin 都能用 | Kotlin 优先，协程 | Java，接口简单 | 体系重 |
| 生命周期 | 绑定得好 | 绑定得好 | 一般 | 有自己的层级 |
| 内存 | 活跃缓存、Bitmap 池 | 较好 | 一般 | 更细，历史方案里还有独立的内存区域 |
| 包体和复杂度 | 中 | 较轻 | 轻 | 重 |
| 动图 | 强 | 够用 | 弱一些 | 强 |
| 社区 | 很大 | 上升快 | 维护相对少 | 特定场景 |

选型一句：新 Kotlin 项目在 Coil 和 Glide 之间按团队语言、动图和已有封装选；历史项目 Glide 最多；只有特别大的图、很深的内存控制才提 Fresco。老的 UniversalImageLoader 知道名字即可。

一条请求要带的不只是 URL：目标尺寸、变换（圆角、中心裁剪）、占位图、错误图、生命周期或协程作用域。缓存 key 必须包含 URL、尺寸和变换，否则同一张原图的圆角版本会把直角版本覆盖掉，或者反过来用错。

查询顺序是内存，然后磁盘，然后网络。网络写回磁盘和内存。内存用 LRU，页面销毁时能取消还没完成的请求。

## 原理（深度，分步骤，讲清为什么）

**1. 为什么不能在主线程直接解码**

一张照片的像素远大于文件大小。`ARGB_8888` 一个像素 4 字节，宽高各 4000 的图是六千多万字节，直接解码就会 OOM。界面上的 ImageView 可能只有 200 像素宽。采样解码是按目标尺寸计算 `inSampleSize`，只解出接近显示大小的 Bitmap。这是图片库最重要的一步，比换一个缓存算法更先讲。

方向信息在 EXIF 里。不处理方向，手机拍的图会躺着。变换（圆角、裁剪）应在采样之后做，在原图上做圆角再缩小，既浪费内存又浪费时间。

**2. 三级缓存为什么是这个顺序**

内存最快，但进程一死就没了，而且占堆。磁盘能跨页面甚至跨进程重启，读一次仍然比网络快。网络最慢也最贵。所以先问内存，再问磁盘，最后才下载。

内存缓存一般是 LRU：最近没用的先丢掉。还要有 Bitmap 池，让同样尺寸的 Bitmap 复用块内存，减少 GC。磁盘缓存要有上限，按 LRU 或版本淘汰，不能把用户存储写满。从网络写回时，先落临时文件再改名，避免读到半张图。

**3. 为什么要合并同一把 key 的请求**

列表里同一个头像出现二十次，不合并就会下二十次、解二十次。引擎用 key 把进行中的请求合在一起，下载和解码只做一次，结果分发给所有 Target。key 如果只有 URL，没有尺寸，一个小头像和一个大图会错误地共用一张图，大图变糊或小图浪费。

**4. 生命周期绑定取消的是什么**

请求发出去之后页面已经销毁，回调再 `setImageBitmap`，要么泄漏 Activity，要么更新到错误的 View。库把请求绑在 Activity、Fragment 或 Compose 的组合上，销毁时取消还没完成的任务，解码结果也不再持有 View。协程版则是跟 `remember` 的 scope 取消。

取消要能中断解码和网络。只把回调丢掉、下载继续，列表快滑时会有一堆无用任务占着线程池和带宽。

**5. 列表里为什么仍会卡**

绑定时机太晚、主线程做了变换、GIF 在主线程解码，都会卡。库应在后台线程解码，主线程只做一次设置 Bitmap。硬件 Bitmap 能减轻一份像素拷贝，但有的版本和有的操作（例如再次读取像素）会失败，要按版本使用，不能无条件打开。

占位图让列表先有东西可看。错误图把失败和「还在加载」分开。缩略图可以用更小的尺寸先显示，再换成目标尺寸。这些都是体验，不改变缓存 key 的规则。

磁盘缓存的文件名用 key 的摘要，不要用完整 URL 当文件名。URL 里有查询串和斜杠，既可能超长，也可能把签名暴露在文件名里。内存里的 Bitmap 不要再被业务缓存到静态 Map：库已经有 LRU，外面再留一份，页面销毁后仍然回收不掉。需要和别的模块共享时，共享的是 URL 和尺寸，不是 Bitmap 对象本身。

GIF 和静图不要走同一个无脑配置。动图会连续解码多帧，列表里同时播放很多 GIF 时，内存和 CPU 都会上去。列表滚动中可以只显示第一帧或静态封面，停下再播。这是策略，不是换库就能自动解决的。Fresco 在这方面控制得更细，所以只有真的卡在动图和大图上才值得付出那份复杂度。

占位图、错误图和取消要分开统计。用户滑走导致的取消不是失败，算进失败率会让图片成功率看起来很差。解码失败和网络失败分开，才能决定是采样尺寸问题还是 CDN 问题。目标尺寸在布局完成前是 0 时不要发请求，否则会解出原图。签名会变的防盗链参数不要进缓存 key，尺寸和圆角则必须进 key。

ARGB_8888 一个像素四个字节，大图不采样会直接 OOM。不需要透明的照片可以更省，该透明的图不能用 565。取消要把任务停掉，不能只是不回调却继续解码，快滑时 CPU 会尖峰。

从网络写回磁盘时先写临时文件再改名，避免读到半张图。失败和取消的结果不要进缓存。

硬件 Bitmap 要看版本，不能无条件打开。

列表里把目标尺寸告诉图片库。

## 使用与实践

业务代码不要自己 `BitmapFactory.decodeStream` 再丢进 ImageView，除非是一次性的小图标。统一走库，才能共享内存池和磁盘缓存。

列表里一定把目标尺寸告诉库，不要下原图再让 ImageView 去缩放。缩放发生在绘制时，大 Bitmap 已经在内存里了。

URL 带防盗链参数时，签名变化不应把同一张图变成永远无法命中的新 key。key 的设计要忽略会过期的签名参数，或者签名稳定在一段时间内。这和 CDN 防盗链是同一件事：403 要重新签发 URL，而不是把坏结果缓存住。

监控成功率和失败原因：网络、解码、取消。取消是用户滑走了，不要算进失败率。大图 OOM 要单独看机型和尺寸。

Compose 里用库提供的 `Image` 或 `AsyncImage`，不要在重组时手动下载。和离线包类似：校验失败或解码失败就显示错误图，不要把半张图留在内存缓存里。

## 例子（至少 1 个完整代码或伪代码块 + 边界场景）

引擎按 key 合并，解码按目标宽度采样。页面销毁则不再投递：

```kotlin
data class ImageRequest(val url: String, val width: Int, val transform: String, val token: Any)

class Engine {
    private val inflight = mutableMapOf<String, MutableList<(Bitmap) -> Unit>>()

    fun load(req: ImageRequest, onResult: (Bitmap) -> Unit) {
        val key = "${req.url}|${req.width}|${req.transform}"
        memory.get(key)?.let { onResult(it); return }
        val waiters = inflight.getOrPut(key) { mutableListOf() }
        val first = waiters.isEmpty()
        waiters += onResult
        if (!first) return // 同一把 key 已经在下
        scope.launch(Dispatchers.IO) {
            val bitmap = decodeSampled(diskOrNetwork(req.url), req.width)
            memory.put(key, bitmap)
            val targets = inflight.remove(key).orEmpty()
            withContext(Dispatchers.Main) {
                targets.forEach { it(bitmap) }
            }
        }
    }
}
```

调用方把生命周期传进去，销毁时从 `inflight` 里移除自己的回调，并在没有等待者时取消任务。

边界一：ImageView 宽高还是 0 就发起请求。采样按 0 计算会出错或解出原图。等布局完成拿到目标尺寸，或由调用方明确传入 dp。列表里用已经知道的 item 尺寸。

边界二：key 只有 URL。先请求了圆角头像，再请求同一 URL 的直角大图，命中圆角那张小图，大图位置显示错。尺寸和变换进 key。

边界三：快速滑动，取消只是不回调，解码仍在进行。滑过一屏会启动几十次解码，主线程虽然没 set 图片，CPU 和内存已经尖峰。取消要传到任务上。

边界四：`ARGB_8888` 解一张没有透明通道的大图，内存是 `RGB_565` 的两倍。不需要透明的照片可以用更省的格式。反过来，该有透明的图用 565 会花。格式按图的种类选，不是全局一个配置。

```text

        │
        ▼

        │
        ▼

        │
        ▼

取消 ≠ 失败
```

## 常见坑与追问（至少 3 条）

1. **Glide 和 Coil 怎么选？** 存量 Java 和已经深度封装的项目继续 Glide。新的 Kotlin 项目 Coil 更轻、和协程更贴。动图和已有封装若强依赖 Glide，不必为了新而换。Fresco 只在极大图和很深的内存控制时再评估，复杂度和包体都更高。

2. **为什么会 OOM，库不是有缓存吗？** 缓存解决的是重复下载，不解决「一次解码出一张巨大的 Bitmap」。必须按目标尺寸采样。列表里不给尺寸，就会按原图解。内存缓存太大也会把堆顶满，大小要有上限。

3. **同一 URL 为什么显示成另一张样式？** 缓存 key 没包含变换或尺寸，不同请求复用了同一份 Bitmap。key 要带上影响像素的所有参数。过期的签名参数则相反，不该进 key，否则每张图都无法命中。

4. **页面关掉了图片回调还来？** 请求没跟生命周期绑定。回调持有 Activity 或 View。销毁时要取消任务并清空 Target。Compose 里跟组合的生命周期走，不要自己在重组里启动下载。

5. **三级缓存是三次各存一份永远不删吗？** 不是。顺序是先查内存再磁盘再网络。内存和磁盘都要淘汰。网络结果写回下面两级。失败和取消的结果不要写进缓存，否则会把错误缓存住。

## 一句话

模块化是把工程拆成 module，解决编译和职责。组件化是这些模块能独立、能组装，并且依赖方向固定。日常口语常把两个词混用。面试要讲清依赖方向、通信方式、发布方式，以及这套治理换来了什么指标。

## 组成与结构

依赖只向下：

```text
app 壳
  → 业务组件（feature）
      → 功能组件 / 中间件（网络、上传、IM、路由、日志）
          → 基础库（工具、基类、构建约定）
              → 平台（Android SDK、native so）
```

业务组件之间不互相依赖。需要对方能力时，用接口下沉、路由，或一条有规范的事件，而不是直接 `implementation(project(":other-feature"))`。

| 通信 | 什么时候用 | 代价 |
|------|------------|------|
| 路由跳转带参 | 打开另一个模块的页面 | 参数要可序列化，编译期不如直接调用稳 |
| 接口下沉，实现上移 | 需要调用能力，例如「打开上传」 | 接口放在下层，实现在上层注册 |
| SPI / 服务发现 | 和上面类似，按接口找实现 | 要管「没人实现」和「实现了两个」 |
| Flow / SharedFlow 总线 | 广播型事件 | 没规范就变成到处发送、没人知道谁在收 |
| EventBus | 老代码里见过 | 难追调用链，新代码慎用 |

初始化用启动任务图，能并行的并行，必须在主线程的才占主线程。不要每个模块一个 ContentProvider 在启动时做网络。

一层 App 的口述可以是：UI（Activity、Fragment、Compose）→ 业务域 → UseCase → 中间件（网络、存储、IM、上传、推送、路由、日志、监控）→ 基础库 → 平台。日志和监控是跨切面，从旁边挂到每一层，而不是让业务互相引用。

## 原理（深度，分步骤，讲清为什么）

**1. 为什么禁止业务环依赖**

A 依赖 B、B 又依赖 A 时，两个模块不能分开编译，也不能单独理解。改 A 的一个页面会把 B 的发布绑进来。环一旦形成，后面的人会继续往环上加代码，因为「反正已经依赖了」。治理的第一步往往是把环拆开，而不是先引入路由框架。

单向依赖让下层不知道上层是谁。基础库不能 `import` 某个业务页面。上层可以依赖下层的接口。这样基础库的发版不再跟着某个业务的文案改动走。

**2. 接口下沉为什么能通信又不形成环**

上传的接口放在中间层：`Uploader`。快传业务和聊天业务都依赖这个接口，不互相依赖。真正的实现在上传模块里，启动时注册进容器。调用方只认接口。测试时换成假实现。这就是依赖倒置：依赖箭头对着抽象，实现细节留在拥有它的模块。

如果接口放在实现模块里，所有人又依赖了实现模块，下沉就失败了。接口模块要保持很薄，不要把实现用的内部类放进去。

**3. 路由解决的是另一类关系**

页面跳转如果写成直接依赖目标 Activity 的类，就回到了模块互相依赖。路由让调用方只拿着一个 path。这和接口下沉互补：要「调用一个能力」用接口；要「打开一个页面」用路由。不要用路由去调一个本该是函数的同步计算，否则类型和错误都会变松。

**4. 初始化顺序为什么是架构问题**

模块多了之后，谁先初始化不再靠 Application 里手写的几十行保证。路由表、网络库、日志，有的要在首屏前，有的可以首帧之后。任务图把「A 必须在 B 之前」说出来，没有依赖的并行，主线程只跑不能后台的那部分。顺序错了的典型现象是：首屏去路由时表还是空的，或者某个 SDK 在 ContentProvider 里做网络，冷启动被拖住。

**5. 治理为什么要分阶段，而不是一次重写**

跨部门时，先有痛点数据：核心库一周被改几次、一次发版要拉上多少人、编译慢在哪一层。然后接口冻结、给兼容窗口、定拥有者和发布制度。直接拆仓库而不冻结接口，业务会在迁移期复制一套私有调用，环变成两份。

快传这条的口径是：跨 5 个部门、20 多人；无用依赖大约减 20%；清理 160 多个类、大约 2 万行；核心库发版频率降大约 90%。发版频率是核心库变更次数在周期前后的对比，靠的是拆分之后业务不再为了改自己的页面去发布核心库。日活近亿、用户超十亿是公司背景，不要说成个人用户数。

风险点要能举实例子：循环依赖、初始化顺序、同步 API 在主线程做网络。最后一个会直接变成宿主的 ANR。

**6. 直播底座是同一套边界的更小版本**

底座只留房间生命周期和信令。课件、白板、上下台是旁边的模块，按产品插上去。变频率不同的东西放在一起，加一个教学工具就要改底座，初中和小学也无法复用。这就是组件边界，不是页面里的 MVVM。

接口模块保持很薄，只放模型和接口，不放 OkHttp、Room 这些实现类型。否则换实现要改所有调用方，下沉就失败了。初始化用任务图写出「谁必须在谁前面」，没有依赖的放到后台或首帧之后。某个 SDK 在 ContentProvider 里建连，会把冷启动的主线程时间加到所有业务上。循环依赖一旦出现就先拆，再谈路由框架，否则路由只是把环藏进字符串。

发版频率下降比较的是核心库在拆分前后的变更次数。业务不再为了改自己的页面去发布核心库，大约能降 90%。无用依赖大约减 20%，并清理了大量类。日活近亿是公司背景，不要说成个人用户数。

## 使用与实践

新代码先问：这段依赖箭头向下吗？业务模块是否只依赖了接口或 path？如果必须引用另一个业务的类，停下来把接口下沉，而不是先把 `implementation` 加上。

发布按层。基础库和中间件要有自己的版本和兼容窗口，业务模块可以跟着 App 发。SDK 对外更严：宿主不一定在你的编译体系里，接口冻结要写进变更说明。

事件总线如果保留，事件要有拥有者，名字里能看出谁发出、谁允许收。禁止把导航、请求结果都塞进一个全局 Flow。

初始化接入启动任务图或 App Startup。能延后的延后到首帧之后，用 IdleHandler 或首帧回调触发，里面不要做重活。

推动时准备一个协商案例：对方要直接依赖你的实现以图省事，你用数据和兼容窗口说明为什么接口冻结更便宜。不要只讲原则。

## 例子（至少 1 个完整代码或伪代码块 + 边界场景）

接口在下层，实现在上传模块启动时注册。业务只认接口：

```kotlin
interface Uploader {
    fun enqueue(req: UploadRequest): Job
}

object Services {
    private val map = mutableMapOf<Class<*>, Any>()
    fun <T : Any> register(type: Class<T>, impl: T) { map[type] = impl }
    fun <T : Any> get(type: Class<T>): T = type.cast(map.getValue(type))
}

class ChatFeature {
    private val uploader = Services.get(Uploader::class.java)
    fun sendFile(path: String) = uploader.enqueue(UploadRequest(path))
}
```

启动任务显式写出依赖，避免靠代码顺序：

```kotlin
tasks.register("router") { /* 装载路由表 */ }
tasks.register("upload") { dependsOn("router"); /* 注册 Uploader */ }
tasks.register("warmup") { background(); dependsOn("upload") }
```

边界一：聊天模块直接依赖直播模块的一个工具类。后来直播模块又要弹聊天页，依赖加回去，形成环。编译和发版绑死。应把工具下沉到基础库，页面跳转改路由。

边界二：接口模块里放了 OkHttp 的类型。所有实现细节漏到了下层，换网络库要改接口。接口只用自己的请求和错误码。

边界三：两个模块都往全局 Flow 里发 `Event("refresh")`。收的一方不知道是谁触发的，测试也无法替换。能调用就用接口，能打开页面就用路由。

边界四：每个 SDK 用 ContentProvider 初始化并在里面建连。冷启动主线程被串行网络占满。改成任务图，连接放到后台，主线程只做注册。

## 画面（text 结构图）

```text
依赖只向下

  app
   ├─ 业务 A    业务 B     业务之间没有箭头
   │     │        │
   │     ▼        ▼
   └─ 中间件：Uploader 接口、路由、IM、日志
              │
              ▼
         基础库 → Android / so

通信
  打开页面  → 路由 path
  调用能力  → 下层接口，上层注册实现
  跨切面    → 日志、监控从旁边挂上，不形成业务依赖

治理顺序
  痛点数据 → 拆环 → 接口冻结 → 兼容窗口 → 拥有者和发布制度
```

## 常见坑与追问（至少 3 条）

1. **模块化和组件化有什么差别？** 模块化强调工程拆分和编译边界。组件化还要求能独立组装：依赖单向、通信有约定、可以按产品插拔。口语里常混用，回答时把依赖方向、通信、发布三件说出来。

2. **业务之间完全不依赖，代码怎么复用？** 复用的代码下沉到功能层或基础层，以接口形式提供。页面入口用路由。不要为了复用一个 Activity 让两个业务互相 implementation。

3. **发版频率下降是怎么来的？** 核心库不再因为上层业务的改动而发布。比较的是核心库在拆分前后的变更次数。快传的口径大约是降 90%，同时无用依赖大约减 20%，清理了大量类。这是耦合下降的结果，不是把提交记录藏起来。

4. **EventBus 为什么不作为主方案？** 发送方和接收方在编译期没有关系，调用链要靠全局搜索。泄漏和重复订阅也不好测。新的跨模块调用用接口或路由。已有总线就规定事件拥有者，不再扩大。

5. **底座里把课件加进去不是更省一次跳转吗？** 课件、白板、上下台的变更频率和产品差异都比房间信令大。放进底座之后，每个产品线都要改底座。拆出去之后初中和小学才能复用同一套房间和信令。

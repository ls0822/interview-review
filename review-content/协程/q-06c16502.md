## 问题
热流「缓存几条」是不是 `replay`？原理？

## 答案
**A：对，SharedFlow 里这个能力就叫 `replay`（重放缓存条数）。**

#### 1. 先分清两个「缓冲」

创建 SharedFlow 时常见参数：

```kotlin
MutableSharedFlow<Int>(
    replay = 2,              // 重放缓存：留给「新订阅者」的历史条数
    extraBufferCapacity = 8, // 额外缓冲：给发射端抗抖动/慢订阅用
    onBufferOverflow = BufferOverflow.SUSPEND // 缓冲满了怎么办
)
```

| 参数 | 给人什么用 | 通俗理解 |
|------|------------|----------|
| **`replay`** | **晚到的收集者**一上来先吃到最近几条历史 | 回看/录像带最后 N 条 |
| **`extraBufferCapacity`** | **已经在听的人**处理不过来时，先堆一下 | 直播间的短暂缓冲 |
| 总缓存上限（概念上） | 约 `replay + extraBufferCapacity` | 历史区 + 临时区 |

所以：问「热流有没有缓存条数」→ 优先答 **`replay`**；完整还会提到 `extraBufferCapacity`。

#### 2. `replay` 原理（说人话）

```text
SharedFlow 内部有一个「重放缓冲区」，最多记下最近 replay 条已发出的值。

新订阅者 collect 时：
  1）先按顺序把缓冲区里的历史值发给他（重放）
  2）然后再接收之后新 emit 的值

老订阅者：正常收实时值；replay 主要是为「后来者」准备的。
```

例子：`replay = 2`

```text
时间线 emit：  A → B → C → D
缓冲区始终保留最近 2 条： … 最终是 [C, D]

此时新来一个收集者：
  先收到 C、D，再收后面的新值
```

- `replay = 0`：晚到的人**拿不到**历史，只收订阅之后的（纯事件总线常见）。  
- `replay = 1`：晚到至少拿到「最新一条」。  
- `replay` 很大：占内存，慎用。

#### 3. 和 StateFlow 的关系

| | StateFlow | SharedFlow(replay=1) |
|--|-----------|----------------------|
| 是否总有值 | 必须有初始/`value` | 可以暂时还没 emit 过 |
| 新订阅者 | 立刻拿到**当前 value** | 重放缓冲区里最近 1 条（若有） |
| 相同值再发 | **默认去重**（equals 相同不发） | **不去重**，相同内容也可连发 |

可以记：

- **StateFlow ≈「带当前状态的热流」**（行为上很像 replay=1 + 去重 + 必有值）。  
- **SharedFlow** 才是通用旋钮：`replay` / 缓冲 / 溢出策略自己配。

#### 4. `emit` 时发生了什么（原理梗概）

1. 值进入 SharedFlow 的缓冲结构；若配置了 `replay`，更新「最近 N 条」重放槽。  
2. 已挂起在收的订阅者被唤醒，按顺序拿到值。  
3. 若有人太慢、缓冲又满：按 `onBufferOverflow`  
   - `SUSPEND`：发射端挂起等；  
   - `DROP_OLDEST` / `DROP_LATEST`：丢旧或丢新。  
4. **没有订阅者**时：热流仍可继续 emit（取决于你怎么用）；`replay>0` 时历史仍会留在重放缓冲里，供以后订阅者回放。

#### 5. 面试怎么说

「热流缓存条数主要指 SharedFlow 的 replay：保留最近 N 次发射，新订阅者先重放再收实时。另外还有 extraBufferCapacity 给在线订阅者做缓冲。StateFlow 必有当前值，新订阅者立刻拿到最新状态，类似 replay=1 且带去重。」

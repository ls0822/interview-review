## 一句话

Socket 是传输层端点的抽象，TCP Socket 最常见。WebSocket 是在 HTTP 上升级出来的全双工长连接，有自己的帧，代理和浏览器更认它。自研裸 TCP 更可控，但要自己处理更多网络环境。IM 两套都见过，选型看可靠性、可达性、耗电和包头，而不是看哪个词更高级。

## 组成与结构

| | 裸 TCP Socket | WebSocket | HTTP 短轮询 |
|--|---------------|-----------|-------------|
| 是什么 | 一条 TCP 字节流 | HTTP 升级后的帧协议，底下仍是 TCP（或可跑在其它传输上） | 反复发 HTTP 请求 |
| 谁解析消息 | 完全自定，通常长度头 + 包体 | 已有帧：操作码、掩码、长度、分片 | HTTP 报文 |
| 全双工 | 是 | 是 | 不是，要等下一次请求 |
| 代理 / 浏览器 | 容易被只放行 HTTP 的网络拦住 | 升级请求看起来像 HTTP，穿透更好 | 最容易通过 |
| 额外开销 | 协议头你自己定，可以很小 | 帧头不大，但握手和掩码有成本 | 每次都带 HTTP 头，最费 |
| 生态 | 自己写重连、心跳、拆包 | 库和网关多 | 实现简单，实时性差 |

Android 上裸 TCP 可以用 Java Socket 或 NIO，也可以用封装库。WebSocket 常用 OkHttp 的实现，它复用 OkHttp 的连接和 TLS，但升级成功之后就不再按普通 HTTP 响应来读。

无论哪一种，长连接都要心跳、退避重连、业务 Ack。WebSocket 的 Ping/Pong 只说明传输还活着，不能代替「消息已入库」的业务 Ack。

## 原理（深度，分步骤，讲清为什么）

**1. Socket 为什么只是端点**

应用要的是「把这段字节送到这个进程」。操作系统用 IP 加端口找到对方，Socket 就是本进程拿着的那个端点句柄。TCP Socket 建立之后是字节流：你 `write` 两次，对方可能 `read` 到一次拼起来的数据，也可能要读两次才凑满。所以裸 TCP 协议几乎一定是「固定长度头里写 body 长度，再读 body」。分隔符和定长也能拆，但 IM 二进制协议用长度头最稳，消息体里可以出现任意字节。

UDP Socket 则保留数据报边界，没有连接握手。IM 主通道很少直接用它。面试说 Socket 时先说清是 TCP 还是 UDP。

**2. WebSocket 升级在做什么**

客户端先发一条 HTTP 请求，带上升级字段和随机的 Sec-WebSocket-Key。服务器用约定算法算出接受值，返回 101。从这个响应之后，同一条 TCP 上不再走 HTTP 文本，而走 WebSocket 帧。这一步的意义是：企业代理、CDN 和浏览器都认识 HTTP，升级成功后却可以双向推数据，不必为了收一条消息再发一个 GET。

帧里有操作码：文本、二进制、Ping、Pong、关闭。长消息可以分片。客户端发往服务器的帧要掩码，这是协议为了防止中间缓存把数据误认成 HTTP。服务器到客户端不掩码。业务如果传 protobuf 或自定义二进制，用二进制帧，不要再套一层多余的 Base64。

**3. 为什么短轮询又费又慢**

轮询是客户端每隔一两秒发一次「有消息吗」。没有消息也要一次完整的 HTTP 往返，头比消息还大，实时性还取决于间隔。间隔改小，耗电和服务器 QPS 一起涨。长连接是有消息才下行。代价是服务器要记住这条连接，客户端要处理断线和心跳。IM 和信令的消息频率不确定，长连接更合适。极低频率的配置拉取用短请求加推送唤醒即可。

**4. 粘包拆包只出现在字节流上**

TCP 不保留 `write` 的边界。一次读可能是半个包（拆包），也可能是两个包粘在一起（粘包）。处理方式是缓冲：先读满头，再按长度读满体，多出来的字节留在缓冲里给下一帧。WebSocket 库已经按帧交给你，一般不用再做 TCP 粘包；如果一帧里面塞了多条业务消息，业务层仍要自己分。裸 TCP 则必须在自己的读循环里做。

超时要分三种。连接超时：握手太久就放弃这个 IP。读超时：太久没有任何字节，可能已经死了。写超时：对端窗口为 0 或网络不通，发送缓冲堵死。只设一个 `soTimeout` 却说不清它作用在读上，排障时会误判。

**5. 选 WebSocket 还是自研 TCP**

WebSocket 适合要过 HTTP 代理、希望用现成网关、客户端还包括浏览器的系统。包头和握手是固定的，省掉一套分帧，但你仍要在帧之上定义业务协议。

自研 TCP 适合协议要极瘦、要完全控制心跳格式、已经有成熟接入层的 SDK。代价是有的网络只放行 443 上的 TLS，裸 TCP 端口可能被丢弃；你还要自己做一切拆包和兼容。很多 IM 的做法是：能直连就走自研 TCP/TLS，连不上再降级 WebSocket。降级是可达性策略，不是两套业务协议各写一次。帧之上的消息号、Ack、压缩应保持同一套。

耗电主要来自心跳频率和唤醒次数，不来自「用了 Socket 这个词」。包头影响的是弱网下的带宽，消息很短时头占比才明显。

升级失败和传输失败要分开。拿到的是 HTTP 401 或 404 时，还没有帧，应该走登录或配置，而不是按断线去指数退避。101 之后才进入帧循环。库如果自带重连，业务状态机就不要再连一次，否则两条连接互相踢。二进制帧里继续用自己的长度和序号，Ping 只证明传输活着，业务 Ack 仍在帧之上。

裸 TCP 必须自己处理粘包和半包：缓冲里先凑满长度头，再凑满包体，多出来的字节留给下一帧。长度要有上限，否则一个巨大数字会把内存打满。WebSocket 库已经按帧切开，业务如果在一帧里放多条消息，仍要自己分。

连接超时、读超时、写超时要分开设。读超时用来发现死连接，设得过大就会把死连接当成活的。

降级只换承载，Ack 和序号保持同一套业务协议，避免两套消息定义。

掩码是协议要求，业务不要再把二进制帧套一层 Base64。

## 使用与实践

OkHttp 的 WebSocket 和普通 Call 共用客户端配置：TLS、证书锁定、代理。它不走「一次请求一个响应」的拦截器完成模型，升级后是回调 `onMessage`。回调所在线程不要直接改界面，切回主线程或写进 ViewModel。连接失败和正常关闭都要进重连状态机，避免 `onFailure` 和主动 `close` 各触发一次重连。

自研 Socket 放在独立读线程或 NIO 循环里，解析出一帧再交给业务队列。不要在主线程 `read`。写操作串行化，避免两个线程同时写一条流把帧头写乱。

和长连接那套配合：鉴权放在升级或握手之后的第一条业务消息，心跳用协议自己的 Ping 或业务心跳，重连退避，消息仍要序号和 Ack。WebSocket 库的自动重连如果和你的状态机各做一遍，会出现双连接。自动重连要么关掉，要么完全交给库并保证只有一个入口。

## 例子（至少 1 个完整代码或伪代码块 + 边界场景）

裸 TCP 按长度头读一帧。不够就继续读，多了就留下：

```kotlin
fun readFrame(input: InputStream, stash: Bytes): Frame {
    while (stash.size < 4) stash += input.readAvailable()
    val len = stash.readInt()
    if (len !in 0..1_048_576) throw IOException("illegal length")
    while (stash.size < 4 + len) stash += input.readAvailable()
    val body = stash.consume(4, len)
    return decode(body)
}
```

OkHttp WebSocket 只负责传输，业务 Ack 仍自己发：

```kotlin
val ws = client.newWebSocket(request, object : WebSocketListener() {
    override fun onOpen(webSocket: WebSocket, response: Response) {
        webSocket.send(authFrame(token)) // 升级成功还不等于已登录
    }
    override fun onMessage(webSocket: WebSocket, bytes: ByteString) {
        session.onFrame(bytes.toByteArray()) // 内部去重、入库，再切主线程
    }
    override fun onFailure(webSocket: WebSocket, t: Throwable, response: Response?) {
        session.onTransportDead() // 交给唯一状态机去退避重连
    }
})
```

边界一：两次 `write` 被一次 `read` 读全。如果按「一次 read 等于一条消息」解析，第二条会把第一条的解析器打乱。必须用长度头和缓冲。

边界二：长度头读到一个巨大数字。没有上限就会按这个长度分配内存，这是协议实现上的拒绝服务。长度要有上限，超过直接断连接。

边界三：WebSocket 返回 101 之前是 HTTP 错误页。这时还没有帧，应按 HTTP 状态处理，例如 401 去刷新登录，而不是当传输抖动去无限重连。

边界四：库已经在 `onFailure` 里自动重连，业务又在回调里 `newWebSocket`。同一账号两条连接互踢，消息乱序。重连入口只留一个。

## 常见坑与追问（至少 3 条）

1. **WebSocket 是不是和 TCP 对立的另一种传输？** 不是。它是跑在 TCP 上的应用层帧协议，握手借用 HTTP。对比的是「裸字节流自研协议」和「升级后的标准帧」，不是对比 TCP 和 UDP。

2. **用了 WebSocket 还要处理粘包吗？** 库把帧切好之后，你拿到的是一条条消息。TCP 粘包由库处理。若一帧里放了多条业务消息，业务层仍要分帧。裸 Socket 则必须自己处理粘包和半包。

3. **Ping 通了能不能算消息可靠？** 不能。Ping/Pong 只说明这条传输还活着。消息可靠要业务 Ack、序号、去重和补拉。对方收到帧但进程在入库前崩溃，Ping 仍可能是通的，消息却丢了。

4. **为什么公司网络里裸 TCP 失败、WebSocket 成功？** 出口只放行 443 和看起来像 HTTP 的流量。自研端口被丢弃。所以 SDK 常把 WebSocket 当降级路径。业务协议保持一套，只换承载。

5. **读超时设很大是不是更不容易断？** 死连接会被当成活的，消息静默丢很久。超时要能发现死连接，再交给退避重连。设得过小则会在弱网上把慢连接误判为死。心跳间隔和读超时要一起定。

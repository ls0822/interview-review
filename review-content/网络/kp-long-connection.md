## 一句话

长连接是一条建好就留着的会话：先建连再鉴权，然后在收发循环里用心跳发现死连接，断了就退避重连并按序号补拉。TCP 可靠只说明字节到了内核，消息要有业务 Ack、去重和本地队列，界面不能等 Ack 才显示。

## 组成与结构

一条可用的 IM 或信令长连接分成这些块，少一块都会在弱网或进程被杀之后露出缺口：

| 块 | 作用 |
|----|------|
| 接入与建连 | 解析地址，建立 TCP（或 WebSocket、QUIC） |
| 鉴权 | 通过后才进入在线态，失败不要当在线 |
| 同步 | 把离线期间的会话和消息补回来 |
| 心跳 | 探测死连接和 NAT 表项，超时就关 |
| 发送队列 | 本地先入库，发送中，Ack 成功或失败再试 |
| 接收 | 按会话序号去重、排序，再入库、上屏 |
| 重连 | 指数退避加抖动，听网络变化，禁止风暴 |
| 状态机 | 空闲、连接中、鉴权中、在线、退避中，转换要唯一 |

融云这条链路的口述顺序就是：解析接入地址并建连 → 鉴权进入在线态 → 同步会话和离线消息 → 心跳保活，发包等 Ack，超时重发 → 收到的消息按会话序号去重排序，再入库上屏。直播底座的信令也是长连接，但底座只负责房间和信令，不把课件协议塞进同一层。

自研 TCP 长连接和 OkHttp 的短请求连接池不是同一条连接，不要混着讲。

## 原理（深度，分步骤，讲清为什么）

**1. 为什么建连之后还要鉴权**

TCP 握手只证明这个地址暂时能收包。谁在用这条连接，要靠 token 或签名。没鉴权就收业务包，任何人都可以对接入地址发数据。鉴权失败应停在失败态并上报，不要进入「在线」然后狂发心跳。鉴权超时和密码错误要分开：前者可以重试，后者要交给登录流程。

**2. 心跳在探测什么**

中间 NAT 会忘掉太久没有数据包的映射，对端进程可能已经死了，而本端的 `read` 还堵着。心跳是一条小的应用层消息：发出去，在规定时间内等响应。响应来了，连接还活。超时了，关掉 Socket，进入重连。不要用「TCP 还显示已连接」代替心跳，内核状态更新得比 NAT 和进程崩溃慢。

间隔是折中。太密费电、服务器连接数高时包也多；太疏，用户会看到一段时间收不到消息还以为在线。弱网把间隔再放得很短，会把已经拥塞的网络打得更满，所以「心跳自适应」要谨慎，不能一丢包就改成几百毫秒一次。

**3. 重连为什么要退避和抖动**

断网恢复的那一秒，所有客户端一起连，接入层会被打满，这就是重连风暴。指数退避让失败次数越多等得越久，例如 1 秒、2 秒、4 秒，封顶 30 秒或 60 秒。抖动是在这个等待上加随机量，避免所有人用同一个公式在同一毫秒醒来。

系统网络从不可用变成可用时，可以立刻尝试一次，不必傻等当前的退避结束。仍要限制「立刻」的次数，网络抖动会在可用和不可用之间快速切换。进前台可以主动检查一次，是否真的还在线用心跳结果判断，不要只看一个布尔值。

**4. 业务 Ack 为什么不能省**

TCP Ack 表示字节进了对方协议栈。对方进程可能在读出来之前被杀死，消息没有入库。发送侧的状态是：本地先插入一条「发送中」→ 写出成功只说明交到了内核 → 收到业务 Ack 才标成功 → 超时则重发或标失败进重试队列。

界面不要等 Ack 才把消息画出来。弱网 Ack 慢，界面会像卡死。先按发送中展示，Ack 到了再改成已送达，失败再允许重试。这和「TCP 已经可靠所以不用管」是两套层次。

**5. 序号、去重、补拉**

重发和重连都会让同一条消息到两次。每条消息在会话内有序号或服务端 id。接收侧见过就丢弃，缺了号就向服务器补拉这一段，而不是把洞留在界面上。乱序到达时先按序号排再上屏，或者先入库由展示层排序。多服务写进同一房间时，到达顺序本身就不稳定，直播切班的做法是进一条队列按序执行，和 IM 的会话内排序是同一类问题。

**6. 状态机为什么必须显式**

没有状态机时，心跳超时和用户手动重连会同时 `connect`，两条 Socket 一起活着，Ack 不知道回到哪条。合法转换类似：

```text
断开 --连接--> 连接中 --成功--> 鉴权中 --成功--> 同步中 --完成--> 在线
  ▲                |失败              |失败
  └──── 退避等待 ←─┴──────────────────┘
在线 --心跳超时或读失败--> 断开
```

同一时刻只允许一个连接尝试。新的尝试开始前，旧 Socket 先关掉。

**7. 与 TCP 可靠、OkHttp 池的易混**

内核 TCP「已连接」≠ 业务在线，要靠心跳与应用 Ack。TCP 确认字节，不确认入库；发送队列须先落库再上屏。OkHttp 连接池与此自研长连接无关。进程被杀后须重新建连、鉴权、补拉，ViewModel 不保留 Socket。

## 使用与实践

读写超时分开设。协议用长度头加包体，处理粘包。心跳包也走这套分帧，不要用一个特殊的裸字节破坏解析器。

进程被杀之后内存里的连接一定没了。冷启动等于重新走建连、鉴权、补拉。ViewModel 救不了 Socket。最近任务划掉也不要假设系统会帮你恢复连接。

toB SDK 的差异放配置和扩展点，不要为一家客户复制一条连接实现。日志回捞能按用户和时间把连接日志拉回来，同时要有开关、脱敏和体积上限。

直播信令与 IM 可以共用这套可靠性词汇：Ack、序号、补拉、退避。房间状态机和消息会话状态机不要塞进同一个类。

## 例子（至少 1 个完整代码或伪代码块 + 边界场景）

发送侧把状态走完，接收侧按序号去重。重连等待带抖动：

```kotlin
sealed interface OutboxState { data object Sending : OutboxState; data object Acked : OutboxState }

class Session {
    private val seen = mutableSetOf<Long>()
    private var attempt = 0

    fun onSendClick(body: String, id: Long) {
        store.insert(id, body, OutboxState.Sending) // 先上屏
        writeFrame(id, body)
        scheduleAckTimeout(id)
    }

    fun onAck(id: Long) { store.mark(id, OutboxState.Acked) }

    fun onIncoming(seq: Long, body: String) {
        if (!seen.add(seq)) return
        store.append(seq, body)
    }

    fun nextBackoffMs(): Long {
        val base = min(1_000L shl attempt.coerceAtMost(5), 60_000L)
        attempt++
        return base + Random.nextLong(0, base / 2) // 抖动
    }

    fun onNetworkAvailable() {
        attempt = 0
        connectIfIdle()
    }
}
```

边界一：Ack 丢了，消息其实已入库。发送侧超时重发，接收侧 `seen` 里已有这个序号，第二次直接丢。如果没有去重，会话里会出现两条一样的消息。

边界二：心跳超时和网络回调同时发生。两边各建一条连接，服务器认为后一条把前一条踢掉，前一条的 Ack 全部落空，客户端开始疯狂重发。状态机要求连接中忽略新的 connect，或者新 connect 之前先关闭旧的。

边界三：补拉时本地已有 1 到 10，服务器从 8 开始推。8、9、10 去重，11 起追加。如果用「清空本地再全量覆盖」且中途失败，界面会先空再失败。补拉应是按洞合并。

边界四：退到后台后系统限制网络，心跳全超时。不要改成 1 秒一次猛探。进前台再连，并保持退避上限。前台服务只用于用户能感知的通话或播放，不作为偷偷保活的理由。

## 画面（text 结构图）

```text
解析地址 → TCP/WS/QUIC 建连 → 鉴权 → 同步离线 → 在线
                                              │
                         心跳 ↔ 响应          │ 超时则关闭
                         发送：本地插入 → 发送中 → 业务 Ack
                                              │ 超时重发（接收侧去重）
                         接收：序号去重 → 排序 → 入库 → 上屏
                                              │
                                         断线 / 网络变化
                                              │
                                    退避 + 抖动 → 重新建连 → 按序号补拉

同一时刻只有一条有效连接
OkHttp 短请求池 ≠ 这条自研长连接
```

## 常见坑与追问（至少 3 条）

1. **有 TCP 为什么还要心跳？** TCP 不会及时告诉你 NAT 已经忘掉映射，也不会及时告诉你对方进程没了。应用层心跳超时是「这条会话不能再用来发消息」的判据。超时就关连接、走重连，而不是一直堵在 `read` 上。

2. **为什么重连不能固定 1 秒一次？** 大面积断网恢复时，所有客户端同一节奏打到接入层，就是风暴。指数退避拉开次数，抖动拉开同一批人的相位。网络变为可用时可以马上试一次，但仍要有次数上限。

3. **界面等 Ack 再显示会怎样？** 弱网下 Ack 可能要数秒，用户以为发送键坏了。应本地先插入发送中，Ack 到达再更新状态，失败进重试队列。Ack 表示业务处理完，不是 TCP 已经确认字节。

4. **消息会丢、会重复、会乱序，各靠什么？** 丢了靠发送超时重发和接收侧补拉；重复靠会话序号去重；乱序靠序号排序后再上屏。三件事都做，才叫这条链路可靠。只做重发不做去重，弱网会刷出重复消息。

5. **进程被杀之后 ViewModel 里的连接还在吗？** 不在。ViewModel 只跨配置变更。进程没了，Socket 一定要重建，并重新鉴权、补拉。划掉最近任务也不要假设系统会恢复这条连接。

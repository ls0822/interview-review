## 一句话

TCP 面向连接，保证字节流可靠、有序，并且带拥塞控制。HTTP、HTTPS 和多数 IM 长连接都跑在它上面。可靠的代价是：丢一个包，同连接后面的数据也要等它，这就是队头阻塞。

## 组成与结构

一条 TCP 连接由两端的地址和端口唯一确定。连接有明确的建立和释放，中间是双向字节流。应用看到的是流，不是一个个和 `send` 对应的消息，所以 IM 要自己做粘包拆包。

| 机制 | 解决什么 | 不解决什么 |
|------|----------|------------|
| 三次握手 | 双方确认能收到对方，并同步初始序号 | 不传输业务数据（除了后来的快速打开选项） |
| 序号 / 确认号 | 对方能说出「连续收到哪一位」 | 不负责你的业务消息边界 |
| 重传 | 丢了可以补 | 补的时候，后面已到的数据也不能提前交给应用（同连接内） |
| 滑动窗口 | 没收到确认也能继续发，直到窗口满 | 窗口为 0 时发送方必须停 |
| 拥塞控制 | 发现网络在丢时主动放慢，避免把网打满 | 不保证延迟，弱网会更慢 |
| 四次挥手 | 两边都发完再关；可以半关闭 | 主动关闭的一方常进入 TIME_WAIT |

UDP 没有这套。要对比时记住：TCP 用握手和重传换可靠，UDP 把取舍留给应用。

## 原理（深度，分步骤，讲清为什么）

**1. 三次握手为什么是三次**

1. 客户端发 SYN，带自己的初始序号 `seq = x`。这是在说「我要建连，我的字节从 x 起编号」。
2. 服务端回 SYN+ACK：`ack = x+1` 表示「你的 x 我收到了」，同时带上自己的初始序号 `seq = y`。
3. 客户端再 ACK：`ack = y+1`。服务端这时才确信自己的序号也被对方收到。

两次不够：服务端发出 SYN 之后，还不知道客户端能不能收到自己。没有第三次，服务端无法确认「我到你」这条方向是通的。序号必须同步，是因为可靠传输靠序号判断「缺了哪一段、重复了哪一段」。两边各自挑初始序号，而不是都从 0 开始，是为了和旧连接里迟到的包错开。

握手完成之后，双方都确认对端可达，并且都知道对方的起始序号。应用数据从这时开始写。

**2. 可靠和有序是怎么做的**

每个字节都有序号。接收方把连续收到的左边界用 ACK 告诉发送方：「这个序号之前的我都有了」。中间缺了一段，发送方超时或收到重复 ACK 就重传这一段。

应用层 `read` 到的数据按序号排好。先到的后面那段不会先交给应用，否则应用会看到乱序字节流。这就是 TCP 队头阻塞：一个包丢了，同连接上已经到达的后续包也要等这个洞补上。HTTP/2 在同一条 TCP 上开很多流，应用层不再因为一个 HTTP 请求堵住另一个，但传输层仍是一条有序字节流，丢包仍会卡住这条连接上的所有流。QUIC 改成在 UDP 上按流独立确认，就是为了避开这一点。

**3. 滑动窗口为什么不是「一个包等一个 ACK」**

停等协议带宽利用率极差：一个往返只能发一个包。窗口表示「没确认也可以先发出去的字节数」，由对方的接收缓冲和对端通告决定。窗口滑到 0，发送方停，等对方把缓冲读走并通告新窗口。这解决的是两端处理速度不一致，不是网络拥塞。拥塞窗口是另一套：发送方自己根据丢包和延迟判断网络还能吃多少。实际能发的量取两者里更小的那个。

**4. 四次挥手为什么比握手多一次**

1. 主动方 FIN：我这边不再发数据了。
2. 被动方 ACK：知道你发完了。这时被动方自己可能还要继续把剩下的数据发完，所以不能把「我也发完了」和这个 ACK 绑死。
3. 被动方发完后，再发自己的 FIN。
4. 主动方 ACK。

第 2 步和第 3 步分开，就是半关闭：一方已经不发了，另一方还能发。如果被动方当时也刚好发完，实现上可以把 ACK 和 FIN 合在一起，看起来像三次，但语义上仍是两边各自关闭发送方向。

主动方发完最后的 ACK 之后进入 TIME_WAIT，大约两个报文最大生存时间。原因有两个：最后的 ACK 如果丢了，被动方会重发 FIN，主动方要还能再 ACK 一次；同时要等旧连接的迟到报文消掉，避免串进同一四元组的新连接。所以会主动关闭的一方（经常是客户端短连接）在高并发下堆积 TIME_WAIT。长连接少握手、少挥手，就是为了避开这段开销。

**5. 拥塞控制在保护谁**

窗口只看对方缓冲，不看中间路由器。所有人按接收窗口往外灌，路由器队列会满，然后大面积丢包。拥塞控制让发送方在丢包或延迟变大时减小发送量，通了再慢慢加。弱网上 TCP 会「越丢越慢」。直播如果用 TCP 传实时帧，旧帧的重传会堵住新帧，所以实时音视频常常改用 UDP，把丢帧策略放在应用里。IM 和控制信令要可靠，仍用 TCP 或在 UDP 上做自己的可靠层（QUIC 就是后一种）。

**6. 和 UDP、QUIC 的易混边界**

TCP 确认的是字节到对端内核，不是业务处理完；IM 的 Ack 仍在应用层。HTTP/2 只解决应用层多请求排队，传输层队头阻塞仍在，要 QUIC 按流确认才缓解。滑动窗口管对端缓冲，拥塞窗口管网络；发送量取两者更严者，不要混成「一个窗口」。

## 使用与实践

Android 上业务一般不手写 TCP 状态机。短请求走 OkHttp，它的连接池复用的就是 TCP 连接，HTTP/2 则在一条 TCP 上多路复用。IM、直播信令如果是自研长连接，那是另一条 Socket，不要和 OkHttp 的连接池说成同一条连接。

长连接要自己做心跳。TCP 活着不代表中间 NAT 还记得这张表，也不代表对端进程还在。读超时、写超时、连接超时要分开设。协议用「长度头 + 包体」划出消息边界，因为 TCP 不保留 `send` 的边界。

线上讲连接时按这个顺序：解析地址、TCP 建连、TLS（如果有）、鉴权、心跳。握手失败、超时、对端重置要分开统计，不要都叫「连接失败」。

## 例子（至少 1 个完整代码或伪代码块 + 边界场景）

用长度头把 TCP 字节流切成消息。缓冲里不够一条就继续读，够了再交给上层：

```kotlin
class FrameReader(private val input: InputStream) {
    private val buf = ByteArrayOutputStream()

    fun readFrame(): ByteArray {
        while (true) {
            if (buf.size() >= 4) {
                val len = readInt(buf.toByteArray(), 0)
                if (len !in 0..MAX_FRAME) throw IOException("bad length $len")
                if (buf.size() >= 4 + len) {
                    val all = buf.toByteArray()
                    val body = all.copyOfRange(4, 4 + len)
                    buf.reset()
                    buf.write(all, 4 + len, all.size - 4 - len) // 多读的留到下一帧
                    return body
                }
            }
            val tmp = ByteArray(4096)
            val n = input.read(tmp)
            if (n < 0) throw EOFException()
            buf.write(tmp, 0, n)
        }
    }
}
```

边界一：一次 `read` 只拿到长度头的 2 个字节。不能把这 2 个字节当成一条消息，要继续读，直到凑满 4 字节头加包体。这就是粘包和半包是同一件事的两面。

边界二：一次 `read` 拿到两条消息外加第三条的一半。解析出前两条之后，剩下的半条必须留在缓冲里，不能丢掉，也不能当成一条完整消息上抛。

边界三：对端进程崩溃，本端还停在 `read`。没有读超时的话，线程会一直堵着，心跳也不会发出去。所以读要带超时，超时再结合「多久没收到心跳响应」决定是继续等还是关掉重连。

边界四：短连接高并发，客户端主动关闭，端口停在 TIME_WAIT，新连接临时发不出去。IM 不该每条消息一次握手，应复用长连接。

**错误对照：** 错法把 TCP 当「一条 read 一条消息」，半包当完整帧上抛、粘包丢后半段。对法：长度头 + 接收缓冲，凑满 `4 + len` 再解析，剩余字节留在 `buf`。

## 画面（text 结构图）

```text
建连
Client                         Server
  |-------- SYN seq=x --------→|
  |←--- SYN+ACK seq=y ack=x+1 -|
  |-------- ACK ack=y+1 ------→|
  双方确认可达，序号对齐，开始字节流

传输
  发送方窗口：未确认也可继续发
  接收方：只按序交给应用；缺一段就形成队头阻塞

释放（主动方常是客户端）
  |-------- FIN ------------→|   我发完了
  |←------- ACK -------------|   知道了（对方还可再发：半关闭）
  |←------- FIN -------------|   我也发完了
  |-------- ACK ------------→|
  主动方 TIME_WAIT（约 2MSL）：等最后 ACK 的重传，并让旧包消失
```

## 常见坑与追问（至少 3 条）

1. **为什么挥手比握手多一次？** 关闭是单向的。被动方收到 FIN 时，自己的数据可能还没发完，所以先 ACK，发完再 FIN。两边都要关闭自己的发送方向。

2. **TIME_WAIT 能不能省掉？** 主动关闭方需要它来重发可能丢失的最后 ACK，并避免旧连接的迟到包被新连接当成数据。正常短连接的 TIME_WAIT 在主动关闭的一端。长连接减少反复建连，比调小系统参数更符合客户端做法。

3. **HTTP/2 是不是已经没有队头阻塞？** 应用层多路复用解决的是「一个请求占着连接、别的请求不能发」。TCP 丢包时，这条连接上所有 HTTP/2 流仍要等这个包重传。要避开传输层队头阻塞，得换 QUIC 这种按流确认的协议。

4. **TCP 已经可靠了，IM 为什么还要 Ack？** TCP 的 Ack 只说明字节到了对方内核，不说明业务处理完、写入了会话、可以展示。进程在 `read` 之后崩溃，TCP 已经确认但消息没入库。业务 Ack 要在「处理完成」之后发。

5. **窗口和拥塞控制是一回事吗？** 不是。滑动窗口看对方还收不收得下。拥塞控制看网络还吃不吃得下。两者都限制发送量，取更严的那个。

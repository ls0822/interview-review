## 一句话

QUIC 是跑在 UDP 上的传输协议，自己带加密、可靠和拥塞控制。HTTP/3 跑在 QUIC 上。它要解决的是 TCP 加 TLS 的握手回合太多、换网就断、以及一条连接丢一个包会堵住上面所有流。

## 组成与结构

| 点 | TCP + TLS + HTTP/2 | QUIC + HTTP/3 |
|----|--------------------|---------------|
| 承载 | 系统 TCP | UDP 上的用户态协议 |
| 加密 | TLS 在 TCP 建连之后再握一次 | 加密做进 QUIC，和传输握手在一起 |
| 建连回合 | 通常 TCP 三次再加 TLS，首次要多个 RTT | 设计目标是首次 1-RTT，再次往往 0-RTT |
| 多路复用 | 多流共享一条有序字节流 | 各流独立确认和重传 |
| 丢包 | 一个洞堵住整条连接上的流 | 只堵住丢失的那条流 |
| 换网 | 四元组变了，连接没了 | 用连接 ID，地址变了可以迁移 |
| 中间设备 | 防火墙熟悉 TCP | 只看到 UDP，有的网络会限制 UDP |

QUIC 不是「不可靠的 HTTP」，也不是把 HTTP 报文原样塞进 UDP。可靠、有序（在单流内部）、拥塞控制和加密都在。不可靠的是再往下的那个 UDP 数据报，丢了由 QUIC 决定重传还是放弃。

Android 上能用到它的路径：新系统的协议栈、Cronet，或自研栈。业务多数时候仍是 OkHttp 走 HTTP/2 或 HTTP/1.1。面试能对比 TCP+HTTP/2 即可，不必声称线上已经全量 HTTP/3。材料里写的「quick」指的就是 QUIC。

## 原理（深度，分步骤，讲清为什么）

**1. 为什么握手能少一个来回**

TCP 要先三次握手，确认双方可达并同步序号，然后 TLS 再交换密钥和证书。这两个阶段串行，首次请求常常要两三个往返才发得出 HTTP。QUIC 把传输参数和加密握手合成一次交换：第一个往返同时完成「我能发 UDP 到你」和「我们算出密钥」。连接曾经成功过，客户端可以在第一个包里就带上用上次信息加密的数据，这就是常说的 0-RTT。0-RTT 的数据有重放风险，只能放幂等、能容忍重放的请求，不能放支付。

**2. 为什么能减轻队头阻塞**

HTTP/2 已经可以在一条连接上同时发出多个请求，再也不会因为「一个请求的响应没读完，下一个请求不能发」而互相挡在应用层。可这些流仍然写进同一条 TCP 字节流。TCP 必须按序号把字节交给上层。一个包丢了，后面包的字节即使到了，也不能先交上去，于是所有流一起等这个洞。

QUIC 的确认号按流计算。流 A 丢了一个包，只重传流 A 的那段；流 B 的后续包可以继续交给 HTTP/3。队头阻塞从「整条连接」缩小到「这一条流」。单条流内部仍是有序的，否则一个文件的字节会乱。

**3. 连接迁移为什么跟连接 ID 有关**

TCP 连接由源 IP、源端口、目的 IP、目的端口确定。手机从 Wi-Fi 切到流量，源地址变了，旧连接在协议上就不是同一条，请求只能重连，TLS 再来一次。QUIC 给连接一个连接 ID，地址只是当前的路径。路径变了，带同一个连接 ID 的包仍属于这条连接，应用不必重新鉴权。这就是换网不断的含义。它依赖两端都实现了迁移，也依赖新路径的 UDP 能通。

**4. 为什么要自己做拥塞控制**

底下的 UDP 没有拥塞控制。QUIC 如果发现能发就拼命发，会把网络打满，旁边的 TCP 流还会退让。所以 QUIC 在用户态实现自己的拥塞控制，丢包或延迟上升时减小发送量。说「QUIC 基于 UDP 所以没有拥塞控制」是错的。没有的是 UDP，有的是 QUIC。

**5. 加密为什么是必选**

TCP 里的序号、标志位中间设备都看得见，有的设备还会改窗口、插入数据。QUIC 把除了少数路由所需字段之外的内容加密，中间设备不能再「帮忙改连接」。好处是行为可预期、演进不用求着所有防火墙升级；坏处是公司网关如果只放行它认识的流量，UDP 或未知加密流量可能被丢掉。所以 HTTP/3 在客户端要能退回 HTTP/2 或 HTTP/1.1，不能假设每张网络都放行 UDP。

**6. 和「弱网更好」的关系**

弱网上 TCP 的问题常常是：丢一个包，整连接停顿，超时重传很保守，换一个基站还要重连。QUIC 用更密的确认、单流重传和连接迁移减轻这三件事。它不会让丢包消失。信号没有时，谁都发不出去。

**7. 降级、0-RTT 与业务会话的边界**

UDP 不通时 QUIC 握手会拖死整次请求，须快速降级 HTTP/2。0-RTT 可被重放，仅幂等读；支付等握手后再发。连接迁移成功 ≠ 业务会话仍有效，鉴权/房间超时看应用心跳。迁移失败时上传仍要按偏移续传。

## 使用与实践

客户端默认仍可以把 OkHttp 的 HTTP/2 作为主路径。要上 HTTP/3，需要服务端和中间网络都通，并准备失败后降级。Cronet 是 Android 上常见的现成栈；系统协议栈是否启用看版本和服务器是否提供 HTTP/3。

不要把 QUIC 和自研 IM 长连接混成一个词。IM 要的是一条能心跳、能补拉、能 Ack 的会话；QUIC 提供的是更好的传输。业务序号、去重、鉴权仍要自己做。0-RTT 只放能重放的读请求。

对比时用四句话就够：更少的握手往返、没有 TCP 那种整连接队头阻塞、地址变了还能迁、加密是内置的。然后补一句：UDP 不通就要退回 TCP 上的 HTTP/2。

直播底座如果媒体走 RTC、信令走自己的长连接，被问到 QUIC 时说明「知道它解决什么，当前这条链路是否启用要按实际栈说」，不要把 RTC 说成 HTTP/3。

## 例子（至少 1 个完整代码或伪代码块 + 边界场景）

客户端优先尝试 HTTP/3，失败一次就退回已经通的 HTTP/2，避免在封锁 UDP 的网上把请求卡死：

```kotlin
class ApiClient(
    private val h3: HttpClient,
    private val h2: HttpClient,
) {
    suspend fun getConfig(): Config {
        return try {
            h3.get("/v1/config")
        } catch (e: UdpBlockedException) {
            h2.get("/v1/config") // 同一条业务请求，换传输，不换鉴权
        }
    }
}

// 0-RTT 只用于幂等读。支付永远等握手完成再发。
suspend fun pay(order: Order) {
    h3.postAfterHandshake("/v1/pay", order)
}
```

边界一：办公室网络丢弃 UDP。QUIC 握手一直超时。如果客户端不降级，所有接口失败，而系统浏览器走 TCP 是好的。监控里要能看出「QUIC 超时后退回 TCP」，不要只看到一个笼统的失败。

边界二：0-RTT 重放。第一次请求是「创建订单」，包被中间复制了一份，服务器处理了两次。0-RTT 数据必须能安全地执行两次，或者服务器拒绝在 0-RTT 里处理这种接口。

边界三：Wi-Fi 切到移动网络。TCP 连接的四元组失效，TLS 和 HTTP 都要重来，进行中的上传从偏移再续。QUIC 连接迁移成功的话，上传流可以沿用。迁移失败（新路径 UDP 不通）仍要走重连和断点续传，业务层不能假设迁移永远成功。

边界四：一条流在传大文件，另一条流在拉配置。大文件丢了一个包。HTTP/2 时配置响应也卡住；HTTP/3 时配置流继续。面试用这个例子说明队头阻塞的差别，比背报文格式有用。

## 画面（text 结构图）

```text
首次（简化）：
  TCP:  SYN → SYN/ACK → ACK → TLS 握手 → HTTP
  QUIC: 一次往返完成传输+加密 → HTTP/3
  再次：QUIC 可能 0-RTT（仅幂等数据）

丢包时的多路复用：
  HTTP/2 over TCP
    流1 [已到][丢][已到]
    流2 [已到]          ← 也要等流1 的洞，因为底下是一条字节流
  HTTP/3 over QUIC
    流1 [已到][丢][已到] ← 只重传流1
    流2 [已到][继续交给应用]

换网：
  TCP  四元组变了 → 连接消失
  QUIC 连接 ID 还在 → 新地址继续
```

## 常见坑与追问（至少 3 条）

1. **QUIC 是不是 UDP，所以不可靠？** 承载是 UDP。QUIC 自己重传、按流排序、做拥塞控制，并强制加密。不可靠的是没被 QUIC 收下的那种裸 UDP。HTTP/3 建立在前者上。

2. **有了 HTTP/2 为什么还要 HTTP/3？** HTTP/2 解决应用层队头阻塞，解决不了 TCP 一个洞堵住所有流，也解决不了换网就断和握手回合多。HTTP/3 把这三件放在 QUIC 里处理。

3. **0-RTT 为什么不能发支付？** 第一个包可能被复制重放。握手完成前，服务器还没法用完整的防重放状态保护这次请求。支付、下单这类不能执行两次的操作，等握手完成再发。

4. **是不是应该全部换成 QUIC？** 有的网络封 UDP，有的服务端没开。客户端要能退回 TCP。栈可以用 Cronet 或系统实现，没有现成栈就先把对比讲清楚，不要说成项目里已经全量。

5. **连接迁移之后业务会话还在吗？** 传输连接可以还在。登录态、房间里的逻辑会话是否还有效，看服务器的会话超时和你自己的心跳，不要以为连接 ID 还在就等于房间状态还在。

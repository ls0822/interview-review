## 一句话

UDP 无连接、尽力交付，不保证到达、不保证顺序、不重传、不做拥塞控制。头很小，应用自己决定丢了怎么办。DNS 查询、直播推流和一部分实时音视频用它；IM 这种不能丢的消息通常不用裸 UDP，要么走 TCP，要么在 UDP 上再做一层可靠协议（QUIC）。

## 组成与结构

UDP 数据报是一条一条的。一次 `send` 对应对面至多一次 `recv`，有消息边界，不像 TCP 那样粘在一条字节流里。没有握手，也没有挥手。对端没人听，发送方仍可能把包交出去，错误要等 ICMP 或应用层超时才知道。

| | TCP | UDP |
|--|-----|-----|
| 连接 | 握手后才传数据 | 知道地址就可以发 |
| 可靠 | 重传、按序交给应用 | 尽力交付，丢了就没了 |
| 拥塞 | 协议自己会放慢 | 协议不管，应用或上层协议管 |
| 边界 | 字节流，要自己拆包 | 数据报边界还在 |
| 头 | 较大（不含选项通常 20 字节起） | 小（8 字节） |
| 常见场景 | HTTP、IM 长连接、文件 | DNS、实时音视频、QUIC 的承载 |

UDP 头里主要是源端口、目的端口、长度、校验和。没有序号，没有窗口。校验失败的包一般直接丢掉，也不会因此触发重传。

## 原理（深度，分步骤，讲清为什么）

**1. 为什么实时媒体更愿意丢，也不愿意等重传**

语音和视频的一帧晚到 200 毫秒，播放器已经播过那个时间点了，重传回来也只能扔掉。TCP 却会因为这一帧丢包，把后面已经到达的新帧一起堵住，延迟越堆越高。UDP 让应用看到「这个包没到」：可以丢帧、可以请求关键帧、可以降低码率，而不是把整条连接停住。

这不是 UDP 更可靠，而是把策略交给应用。文件传输不能这么做，少一个字节文件就坏了，所以下载走 TCP 或带校验和补包的可靠通道。

**2. 为什么说它无连接，但业务里仍要「会话」**

UDP 协议本身不记得对方是谁。服务器收到数据报，只知道这个包从哪个地址来。登录态、房间号、加密密钥都要应用自己在包里带，或者自己用地址加一层会话表。NAT 也不认识「连接」，只是暂时记住「这个内网端口最近发过包」。安静太久，NAT 表项过期，对面再发回来就进不来。所以即使用 UDP，实时通话仍要周期性发小包，让中间设备记住这条路径。这和 TCP 长连接的心跳是同一类问题，只是 UDP 连「连接还在不在」都没有协议状态可看。

**3. 不保证顺序时长什么样**

后发的包可以先到。播放器如果按到达顺序播，画面会回跳。应用要自己带序号或时间戳：旧包直接丢，缺口选择等待很短一段时间或直接跳过。TCP 是内核帮你排好再给应用；UDP 是应用看到原始到达顺序。

**4. 没有拥塞控制会怎样**

发送方可以按固定码率一直发。网络已经丢了，它仍按原速发，丢包会更严重，旁边的 TCP 流还会因为拥塞控制主动让路，形成「UDP 把带宽占满、TCP 越来越慢」。所以真正在公网跑的 UDP 协议，例如 QUIC 和成熟的 RTC，会在 UDP 之上自己做拥塞控制。裸 UDP 只适合查询量小、或码率受应用严格限制的场景。

**5. DNS 为什么用 UDP**

一次域名查询通常一个来回就能装下，没有必要先握手再查询再挥手。丢了就由解析器再问一次。响应太大时才会改走 TCP。这和「UDP 适合短请求」是一回事：交互本身很短，握手的成本比丢一次再问更贵。

**6. 和 QUIC 的关系**

QUIC 跑在 UDP 上，但 QUIC 不是「不可靠的 HTTP」。它自己做了加密、重传、按流确认、拥塞控制和连接迁移。选 UDP 是因为操作系统和中间网络已经放行 UDP，而在用户态实现新的可靠传输，不必等所有系统升级 TCP。面试说 QUIC 时不要把它和裸 UDP 画等号。

**7. 和裸 UDP、QUIC 的易混边界**

QUIC 跑在 UDP 上，自带重传、拥塞与加密，不能和「裸 UDP + 自己什么都不做」等同。`send` 成功只表示本机交出去；对端未监听、NAT 过期、中途丢包都不会反映在返回值里。实时媒体可丢旧帧，信令和 IM 须可靠层；单包宜控制在路径 MTU 内，避免 IP 分片丢一片整报文消失。

## 使用与实践

客户端选型先问数据能不能丢、晚到还有没有用。

- 不能丢、要按序处理完：TCP 或 QUIC。IM 消息、信令、文件、API 走这里。
- 晚到就无用、可以丢帧：UDP 上的实时媒体。直播推流、通话的音视频包。控制面（进房、上下麦）仍要可靠通道，不要和媒体包混成一种不可靠发送。
- DNS：系统解析默认 UDP。HTTPDNS 则是用 HTTPS 去问，那是应用层优化，底下仍是 TCP/TLS，不是改用 UDP 查询。

Android 上 Java `DatagramSocket` 可以发 UDP。超时必须设，因为协议不会告诉你「对方没收到」。包长不要超过路径 MTU，否则会被分片，分片丢一片整包就没了。实时场景更常见的是用 RTC SDK，而不是业务自己维护 UDP 重传。

直播底座里：音视频是 RTC 出画，课件翻页这类不能错的事件走信令可靠通道。不要说成「底座全部走 UDP」。

## 例子（至少 1 个完整代码或伪代码块 + 边界场景）

接收端按序号丢掉过期语音包，只播更新的一包。没有这层判断，乱序会把声音播回去：

```kotlin
class AudioJitter(private val maxLateMs: Long) {
    private var nextSeq = 0L

    fun onPacket(seq: Long, sentAtMs: Long, payload: ByteArray, now: Long) {
        if (seq < nextSeq) return                 // 旧包，播了会回跳
        if (now - sentAtMs > maxLateMs) return    // 晚到，时间点已经过去
        nextSeq = seq + 1
        play(payload)
    }
}
```

发送侧要限制自己，不能因为 UDP 不拥塞控制就一次把队列打光：

```kotlin
fun sendVideo(socket: DatagramSocket, packets: List<ByteArray>, addr: SocketAddress) {
    for (p in packets) {
        if (p.size > MAX_DATAGRAM) error("超过路径可承受的单包，会被分片")
        socket.send(DatagramPacket(p, p.size, addr))
        pace() // 按目标码率间隔发送，而不是 while 里打满
    }
}
```

边界一：对端进程没启动。`send` 仍可能成功返回，因为本机只负责把包交出去。没有应用层 Ack 或超时，调用方会以为已经送达。UDP 的「发出去」不等于「对方处理了」。

边界二：NAT 静默 30 秒。中间设备把映射删了，服务器按旧端口回包，客户端收不到。看起来像「服务器没发」，实际是回程路径断了。需要周期性小包刷新映射，间隔要小于常见 NAT 超时，同时又不能密到耗电。

边界三：一个数据报被 IP 层拆成多片，最后一片丢了。应用收不到这一整个数据报，也没有「半条消息」可以解析。所以实时包要控制在一个 MTU 内。TCP 则是字节流，没有这个「整包消失」的形态，但会重传。

边界四：把 IM 消息直接放进 UDP 且不做序号和重传。弱网丢一条，会话就缺消息，对面还不知道。IM 要么用 TCP 长连接，要么做完整的可靠层，不能只因为「UDP 快」就拿来发消息。

**错误对照：** 错法认为 `DatagramSocket.send` 返回 true 就等于对端已处理——NAT 断映射、对端未监听都会静默丢包。对法：信令走 TCP/可靠层；实时媒体用 UDP 也要序号 + 过期丢弃 + 应用层 Ack/心跳。

## 画面（text 结构图）

```text
应用                         应用
  |  send(datagram)            |
  |-------- 数据报 ----------→|   可能丢失
  |-------- 数据报 2 --------→|   可能先到
  |   （没有 SYN/FIN）         |
  |←------- 晚到的数据报 1 ----|   应用自己决定丢弃还是使用

和 TCP 的差别：
  TCP：内核重传、按序交给 read()，丢包堵住同连接后续
  UDP：内核不重传、不排序；策略在应用或 QUIC 这种上层

实时媒体：旧包丢弃，新包继续
文件/IM：不要停在裸 UDP
```

## 常见坑与追问（至少 3 条）

1. **UDP 是不是一定比 TCP 快？** 少了握手和重传，单次短请求的开销更小，DNS 就是这样。一旦你在上面补上可靠、加密和拥塞控制，延迟优势要重新算。实时场景快，是因为允许丢旧包，不是因为 UDP 头少了十几个字节。

2. **有消息边界，是不是就没有粘包？** 一个数据报不会和另一个粘成一次 `recv`。但数据报可以被 IP 分片，分片丢失则整包消失；应用如果自己在一个数据报里塞了多条消息，仍要自己分帧。不要把 TCP 的粘包处理原样套过来，也不要假设一个包永远小于 MTU。

3. **直播是不是全程 UDP？** 媒体包常常是 UDP。进房、上下麦、课件翻页要可靠，走 TCP 长连接、QUIC 或 RTC 里单独的可靠通道。丢一帧画面和丢一条「翻页」信令不是同一种失败。

4. **为什么 QUIC 还要基于 UDP？** 中间网络和操作系统对 UDP 的放行比对「改 TCP」现实。QUIC 在用户态补上可靠和加密，并按流独立重传，避开 TCP 队头阻塞。它不是裸 UDP。

5. **`send` 返回了能不能告诉用户已发送？** 不能。返回只说明本地协议栈接受了这份数据报。对方没监听、NAT 过期、中途丢弃，都不会反映在这次返回值里。要送达确认，必须有应用层响应或上层可靠协议。

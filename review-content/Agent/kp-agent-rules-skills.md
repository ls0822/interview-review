## 一句话

Rules 管每条对话都要遵守的短规矩，Skills 管遇到某类事才加载的步骤说明书，MCP 把仓库以外的工具接进来，Plugin 把这三样和钩子打成一包分发给团队。

## 组成与结构

| | 是什么 | 什么时候用 | 例子 |
|--|--------|------------|------|
| Rules | 打开项目就生效的短规矩 | 每条对话都要遵守 | 用 Kotlin、别改公开签名、回答用中文 |
| Skills | 「遇到这类事按这个步骤做」的说明书，用到才加载 | 重复的长流程 | 排查：先拉日志、再对源码、输出固定模板 |
| MCP | 接外部工具的协议，Agent 通过它调你的服务 | 要读仓库以外的活数据 | 日志平台、缺陷单、设计稿、浏览器 |
| Plugin | 把 rules、skills、MCP、钩子收成可安装的包 | 分发给同事 | 团队的 Android 排查包 |

关系就一句：Rules 管规矩，Skills 管步骤，MCP 管手脚，Plugin 管分发。

和 Gradle 类比着记：Rules 像 `gradle.properties` 里的约定，Skills 像一份操作文档，MCP 像你暴露的 API，Plugin 像把它们收成一个可安装的包。类比只帮助记忆，不要说成 Gradle 插件在运行时调模型。

Cursor 市场上的 Plugin 本身不按件收费。真要收费，放在你自己的服务上，例如日志查询配额，不要把 Plugin 当成商品去卖。

## 原理

1. **Rules 为什么必须短。** 它们进的是每轮都在的上下文。写成长教程会挤掉代码和日志，模型对每条的遵守也会变差。一条规则只写可检查的约束：语言、不能动的目录、提交前要跑的命令、回答用哪种语言。具体「如何排查一次 ANR」不要放这里。
2. **Skills 为什么按需加载。** 长流程偶尔才用。每次都塞进上下文，既贵又干扰无关任务。技能文件描述触发条件（用户在查崩溃、在加一个页面）和步骤。模型判断要做这类事时才读入。步骤要写到有输入、有输出、有停止，而不是「请仔细分析」。
3. **MCP 是工具的插座，不是模型。** 服务器把若干工具以统一协议暴露出来：名字、参数模式、返回文本或资源。Agent 决定调用哪一个。日志平台因此不用把密钥和查询语句写进提示词里让模型自由发挥 HTTP。权限、脱敏、超时放在服务器一侧。模型只看到允许它看的结果。
4. **Plugin 解决的是分发。** 一个人机器上能跑的 rules、skills、MCP 配置，同事没有。Plugin 把它们打包，安装后路径和开关一致。钩子（例如保存时、提交前）若也要统一，一并放进包里。它不增加新的智能，只减少「每个仓库口头抄一份」。
5. **和仓库里的代码review 怎么配合。** Rules 可以要求「只改某模块、公开 API 不动」。Skills 可以要求「先复述调用链再改」。MCP 可以要求「结论必须附日志行号」。三者叠在同一次排查上：规矩始终在，步骤在触发时在，证据从外部工具来。
6. **边界。** Skill 不会在你没装的时候自动存在于云端模型里。MCP 服务器挂了，Agent 就少一只手，应当失败得看得见，而不是静默改用猜测。Plugin 版本要跟仓库约定一起升级，否则团队一半人还在用旧的日志字段。

## 使用与实践

排查包可以这样拆，面试时按这四层说：

- Rule：不改线上开关和混淆 keep；结论必须带文件路径；不把用户 id 写进提交说明。
- Skill：输入是现象、房间、时间；步骤是拉日志、定位类、按模板输出原因和置信度；停在等人确认。
- MCP：一个日志查询工具，参数是房间、用户、时间窗，服务端做权限和脱敏。
- Plugin：把上面三样发给客户端组，新同事装上就能用同一套。

写代码的规则另放一份，不要和排查技能混成一个长文件。例如「新页面沿用现有结构、不要引入第二套网络库」。

密钥放在本机 MCP 配置或服务端，不写进 Skill 正文。Skill 可以提交到仓库，密钥不行。

四层不要互相替代。把查询语句写进 Rule，每轮都会带着一段用不上的日志语法。把「必须用中文」写进 Skill，没触发技能时这条规矩就不存在。把脱敏做在提示词里而不是 MCP 服务端，模型一旦被要求「原文贴出来」就可能把规则说漏。Plugin 只解决同事装得齐，不代替服务端的鉴权。

## 例子

技能步骤压成模板，而不是一段散文：

```text
输入：现象、房间号、用户、时间窗
1. 调日志工具拉取该时间窗
2. 从报错里抽出类名和信令名，在仓库中打开对应文件
3. 输出：可能原因、代码位置、建议先看的下一处、不知道的部分
4. 停止。不要改文件，不要发版
```

规则侧只有短句：「公开 SDK 方法签名不能改」「回答使用中文」「禁止移动混淆 keep 清单，除非人明确要求」。

MCP 工具的参数示意：

```text
query_logs(roomId, userId, from, to) -> 已脱敏的文本，最多 N 行
```

Agent 不能自己拼一个无限制的全量导出。这就是工具边界。

## 画面

```text
每轮都在：Rules（短）
触发才读：Skills（步骤）
仓库之外：MCP（日志 / 单子 / 浏览器）
装到别人机器：Plugin 把上面打包

Gradle 类比：约定 / 文档 / API / 可安装的包
```

## 常见坑与追问

1. **把排查教程全写进 Rules。** 追问：有什么坏处？每轮都占上下文。长步骤放 Skill，用到再加载。
2. **说 MCP 是另一个模型。** 追问：它实际提供什么？工具的名字、参数和返回。推理仍是原来的模型。
3. **Plugin 拿去卖安装包。** 追问：收费放哪？放自己的服务。市场上的 Plugin 是分发方式。
4. **密钥写在 Skill 里提交。** 追问：应该放哪？本机或服务端的 MCP 配置。Skill 只写步骤。

## 一句话

人定范围和验收，Agent 起草和修改，人看 diff 再落地；排查则是一条固定流水线：拉日志、对源码、给初判，确认之前不改线上。

## 组成与结构

两套用法不要揉成「AI 什么都能做」。

| 场景 | 形态 | 人做什么 |
|------|------|----------|
| 排查线上问题 | 固定流水线，步骤和输出模板稳定 | 提供现象，确认初判，决定改不改 |
| 写业务代码 | IDE / 终端里的 Agent | 写清范围，看 diff，跑编译或指定检查 |
| 样板和草稿 | 补测试、套现有页面结构、改命名 | 把草稿收成符合模块边界的代码 |
| 高风险改动 | 协议、权限、混淆 keep、线上开关 | 只让它拟草稿，人自己改完 |

一次写代码任务的材料就四样：目标、相关文件、不能改的约束、怎样算做完。缺一个，它就会在仓库里自己猜。

数字口径单独放在口述末尾，避免和流程混：

1. 正确率 80%～90% 是抽样，样本是已有结论的问题，比的是初判是否指向同一原因。
2. 耗时降 90% 以上，省的是翻日志和对源码，不含确认和改代码。
3. 它不是自动发版。
4. 日志有范围、脱敏和权限。

## 原理

1. **为什么排查用流水线。** 步骤是固定的：按房间、用户、时间拉日志，用报错和类名找源码，输出原因、位置和建议。固定步骤才能量化「初判是否和事后结论一致」。自由聊天每轮问法不同，无法验收，也容易在没看到日志时就开始改代码。
2. **为什么写功能用 IDE Agent。** 改动必须落在 diff 里被人看。终端 Agent 适合跨很多文件并自己跑构建。云端代理若没在生产用过，就说没用过。Dify / Coze 用来搭「拉日志然后通知」这类业务流可以，不拿来改 Android 工程。LangGraph 一类适合你要把分支和人工卡点写成代码时再提。
3. **上下文越小越准。** 仓库大了，先点名模块和路径。把无关的第二个业务线也打开，它会模仿错误的那套风格，或修改不该动的文件。Rules 里写死模块边界，比每次口头提醒可靠。
4. **计划先于大改。** 先要一份计划：动哪些文件、不动什么、如何验证。人改计划，再让它动文件。跳过这一步，diff 会混进重构、重命名和无关格式化，review 成本高于手写。
5. **错误要带着证据回去。** 编译失败就把编译输出贴回同一轮，不要新开一句「再试试」。新开一句会丢掉刚才的约束。测试同理：点名哪条路径要点，哪条命令要过。
6. **高风险区人做最后一笔。** 协议字段、权限声明、R8 keep、远程开关，错了要等发版才爆。Agent 可以列出它认为要改的行，人自己改。这和排查里的停机条件是同一原则：自动化停在「建议」，提交停在人。

多智能体（规划、写码、审查分开）知道概念即可。步骤已经固定时，一条流水线更稳，也更省。

## 使用与实践

适合交给它：已有写法的新页面、补测试、改命名、先讲一条调用链给你核对。

不要整包扔给它：「把直播底座重构了」。没有人看 diff 就提交。没有验收标准的「优化一下」。

推荐的一轮：

1. 写清目标和不能动的目录。
2. 大改先看计划。
3. 只打开相关模块。
4. 看 diff，跑编译或你指定的检查。
5. 失败日志原样贴回。
6. 同一类要求写进 Rules，不要每次重说。

口述时主动把「工具做了什么」和「人拍板什么」拆开。工具负责把日志裁到时间窗、把堆栈对上类名、把可能原因写成固定模板。人负责判断这是不是根因、改不改、何时上线。这样被追问「那不就是自动修 bug 吗」时，答案是否定的：流水线停在初判，提交停在 diff。数字也按同一刀来切，避免把抽样准确率和发版成功率说成一个数。

面试 1 分钟可以把两套用法接起来：排查 Agent 是固定流水线，抽样正确率 80%～90%，省的是翻日志的时间，人确认后才改。写代码用 Cursor 或 Claude Code，任务写清范围和验收，diff 必须人看。Rules 放规矩，Skills 放重复步骤，MCP 接日志，Plugin 把这套发给团队。

## 例子

写代码的任务说明可以短到这样：

```text
目标：给设置页增加「消息免打扰」开关，走现有 SettingsRepository。
只能改：feature/settings 下的页面、ViewModel 和已有的偏好读写。
不能改：网络层、混淆 keep、任何 public SDK 签名。
做完：编译通过；打开页面能看到开关；重复进入仍保持上次的值。
先给计划，我确认后再改文件。
```

排查的输出模板：

```text
现象：房间 1001，21:03 后收不到信令
日志：心跳在 21:02:40 之后没有再写（附行）
代码：HeartbeatWriter，路径 ...
初判：写心跳前抢到了主线程上的锁，线程被堵住
建议先看：那把锁的持有栈
不改代码。
```

人若不同意初判，就停。下一轮只补充新的日志范围，不把任务改成「顺便重构心跳」。

## 画面

```text
排查：现象 -> 拉日志 -> 对源码 -> 初判 -> 人确认 -> 才可能改
写代码：范围 + 验收 -> 计划 -> diff -> 人看 -> 编译/检查 -> 落地

两边相同的一点：自动化停在可审查的产物，不停在无人看过的提交
```

## 常见坑与追问

1. **把耗时下降说成研发整体快了 90%。** 追问：省的是哪一段？翻日志和对源码。确认和改代码还在。
2. **没看 diff 就说 Agent 已经修好了。** 追问：你怎么知道没改到协议？看 diff，并自己跑约定的检查。高风险文件人改。
3. **为什么不用一个万能对话完成排查？** 追问：怎样验收？固定模板才能和事后结论对比，才有 80%～90% 的样本。
4. **任务只写「重构直播」。** 追问：应该补哪四样？目标、文件范围、禁止改动、验收方式。大改还要先确认计划。

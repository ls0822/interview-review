## 一句话

写功能：**人定范围与验收，Agent 出 diff，人看再落地**；排查：**固定流水线产可对比初判，确认前不改线上**——两套流程共用一条原则，自动化停在可审查产物上，不停在无人看过的提交。

## 组成与结构

场景分栏（防揉成「AI 万能」）：

| 场景 | 形态 | 人的卡点 |
|------|------|----------|
| 线上排查 | 流水线 + 模板输出 | 确认根因、决定改不改 |
| 功能开发 | IDE/终端 Agent | 范围、计划、diff、检查 |
| 样板扩写 | 补测试、套页面结构 | 收成模块边界内代码 |
| 高风险 | 协议、权限、keep、开关 | 仅草稿，人落最后一笔 |

写代码任务四要素缺一会乱猜：**目标、相关路径、禁止改动、验收标准**。大改加第五步：**先计划后动文件**。

数字口径独立记忆（与流程绑死以免口述穿帮）：

1. 初判正确率 80%～90% → 已有结论问题的抽样。
2. 耗时降 → 翻日志/对源码，不含确认与编码。
3. 非自动发版。
4. 日志范围、脱敏、权限。

## 原理

1. **排查用流水线因可验收。** 固定步骤（拉日志→对齐类→模板输出）才能和事后结论逐条对比；自由对话每轮问法不同，无法统计，也易无日志就改码。
2. **写功能用 IDE 因 diff 是契约。** 改动必须可 review；终端适合跨模块 + 跑构建。编排框架适合分支/人工闸口写成代码时再提，不是默认必上。
3. **上下文越小越准。** 大仓库先锁模块路径；打开无关业务线会模仿错风格或改错目录。Rules 写边界优于口头重复。
4. **计划先于大改。** 计划列动哪些文件、不动啥、怎么验；人改计划再执行。跳过 → diff 混重构/格式化，review 贵于手写。
5. **错误要带证据回流。** 编译/测试失败把**完整输出**贴回同轮对话，新开会话丢约束。这是 Agent 工作流的「反馈环」，不是客气用语。
6. **高风险人收尾。** 与 Agent 定义里的停机同构：自动化止于建议，提交止于人。多 Agent 角色在步骤已固定时常不如单流水线。

与 CI 对比：CI 验证已写进的规则；Agent 在写之前探索；CI 不能替人定产品边界。

## 使用与实践

适合：新页面跟现有结构、补测试、改命名、让它先画调用链核对。

不适合：无范围「重构直播底座」、无 diff review 的提交、无验收的「优化一下」。

推荐一轮：目标+禁区 → 大改要计划 → 少开无关模块 → 看 diff → 跑约定检查 → 失败日志原样回灌 → 重复要求写进 Rules。

口述拆清：**工具裁证据，人判根因与上线**；被问「是不是自动修 bug」答否——停在初判，提交停在人。

## 例子

写代码任务卡：

```text
目标：设置页「消息免打扰」，走 SettingsRepository
只改：feature/settings 页面、VM、偏好读写
禁止：网络层、keep、public SDK 签名
验收：编译过；开关持久；重复进入状态对
先计划，确认后改文件
```

排查模板：

```text
现象 / 日志摘要 / 代码路径 / 初判 / 建议下一眼 / 不改代码
```

错例：人不同意初判却让 Agent「顺便重构心跳」——范围膨胀，验收失控。对例：只补新时间窗重跑日志步骤。

## 画面

```text
排查：现象→日志→源码→初判→人确认→(可能)改
编码：范围→计划→diff→人看→检查→落地
共同：停在可审查产物
```

## 常见坑与追问

1. **耗时降 = 研发总快 90%。** 追问：省哪段？取证与对码，不省确认编码。
2. **没看 diff 说已修好。** 追问：协议/keep 怎么保证？人看 diff + 约定检查。
3. **万能对话排查。** 追问：没有固定模板就无法做抽样评测。
4. **任务只有「重构直播」。** 追问：补四要素 + 大改先计划。
5. **每轮新开对话重讲规矩。** 追问：应沉淀到 Rules，减少漂移。

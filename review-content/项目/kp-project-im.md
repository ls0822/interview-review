## 一句话

IM SDK 把连接、消息、存储和推送协同收在一条会话里：建连、鉴权、同步离线，然后心跳保活；发送要等业务 Ack，接收按会话序号去重排序再入库上屏。断线后退避重连并按序号补拉。界面先显示发送中，不等 Ack 才出现。

## 组成与结构

从连接到消息出现：

1. 解析接入地址，建连。
2. 鉴权，通过后进入在线态。
3. 同步会话和离线期间的消息。
4. 心跳保活。发包，等 Ack，超时重发。
5. 收到的消息先按会话序号去重、排序，再入库、上屏。

内部模块分开：连接（含心跳和重连）、会话与收发、存储、推送协同。推送负责把进程拉起来或提醒用户，不代替长连接上的可靠投递。进程在前台时以长连接为准；连接不在时，推送把人带回来，回来之后仍要补拉，不能只显示通知里的那一段摘要。

发送侧状态：本地先插入 → 发送中 → 收到 Ack 标成功，或失败进入重试队列。接收侧：去重集合加序号空洞的补拉。

toB 是上千家客户。差异走配置和扩展点，不在主干上复制一套连接。日志回捞按用户和时间把日志拉回来，同时要有开关、脱敏和体积上限。这和后来的排查 Agent 是两代工具：以前是规则分析，后来是拉日志再对源码，人确认后再改。

快传 IM 2.0 同样讲可靠性与长连接。两边的差别是：融云是 toB PaaS，主干面对很多客户的接入；快传是亿级 App 里的一条 IM。不要把两套用户数说成同一个数。融云的量级是千万日活级 SDK，按材料说，不另编。

## 原理（深度，分步骤，讲清为什么）

**1. 为什么鉴权在建连之后、同步之前**

TCP 或 WebSocket 连上只说明管道在。不鉴权就同步消息，等于谁都能把管道当成某个用户。鉴权失败停在失败态，把登录过期和网络超时分开：过期交给账号流程，超时进入退避。没鉴权成功不去拉离线消息，避免空 token 把服务器打出一串 401。

**2. 同步为什么在进入「可发送」之前**

刚连上就允许发送，本地序号和服务器不一致，新消息会插进空洞里，补拉回来又重复。顺序应是：鉴权通过，拉会话和离线消息，把本地缺口补上，再进入在线，开始心跳和发送。同步失败就不要标成已在线。

**3. 业务 Ack 和 TCP Ack 差在哪**

TCP 确认的是字节进了对方内核。对方进程在入库前被杀，消息会丢，而发送方以为写成功了。业务 Ack 要在服务器接受并落库之后返回。超时未收到就重发。重发必然带来重复，所以接收侧用会话内序号或消息 id 去重。

界面如果等 Ack 才插入气泡，弱网会停几秒，像发送键失灵。本地先插入发送中，Ack 到了改状态，失败才允许用户重试。存储也先落这条本地消息，进程被杀后还能看到「未发送」而不是凭空消失。

**4. 乱序和补拉**

同一会话内以序号为准，不以来包顺序为准。先到了 11、后到了 10，就先排再展示，或者先入库由查询按序号输出。缺了 10 只来了 12，向服务器补拉这一段，而不是把 12 先显示成下一条导致中间永远空着。

多端同时发、重连后又推了一遍，都靠同一套去重。补拉和实时推送可能重叠，重叠部分丢弃，不能先清空本地再全量灌入，中途失败会把会话刷空。

**5. 断线重连和风暴**

系统网络回调触发重连，不要只靠心跳慢慢发现「网络图标已经回来了」。间隔指数退避，并加抖动，避免所有用户在网络恢复的同一秒打满接入层。连上之后走的仍是鉴权、补拉，不是假设旧 Socket 上的发送缓冲还在。

同一时刻一条有效连接。心跳超时触发的重连和网络回调触发的重连要进同一个状态机。推送点击进会话时，如果连接正在建，就等这次结果，不要再开一条。

**6. 定制和日志为什么是可靠性的一部分**

一家客户改了心跳或协议就开分支，修复丢消息的补丁合不回所有分支，可靠性会只存在于主干演示里。配置和扩展点让主干继续收这一份修复。

没有日志就无法区分是 DNS、鉴权、心跳超时还是序号空洞。回捞要能定位到用户和时间，又不能把消息正文和 token 拉走。体积上限避免把用户网络打满。开关默认收紧。

推送不是消息的第二份正文。通知负责把人带回 App，会话内容以长连接和补拉的序号为准，否则旧通知会插进一条已经存在的消息。同步完成之前不要把状态标成在线，否则新发送会插进还没补上的空洞。clientId 让服务器对重发幂等，接收侧再用序号去重。401 和超时分成不同错误码，避免把登录过期重试成重连风暴。

本地先插入发送中，Ack 到了再改成已送达。界面等 Ack 才出现气泡，弱网会像卡死。进程被杀后这条未发送的记录还在库里，而不是凭空消失。去重和补拉一起做，只重发不去重，会话里会看到两条一样的内容。

日志回捞要有开关、脱敏和体积上限，才能按用户和时间定位，又不会把消息正文带走。

## 使用与实践

白板可以画两条：连接状态机（断开、连接中、鉴权、同步、在线、退避），以及发送时序（本地插入、发送中、Ack、失败入队）。口述从「解析地址」讲到「上屏」，大约八分钟。

协议用长度头加包体。心跳、读写超时都要设。WebSocket 或裸 TCP 是承载选择：要过代理用 WebSocket 或准备降级，协议层的 Ack 和序号保持一套。

和直播信令共用词汇：心跳、退避、序号、补拉。不要共用一个状态机类。房间切班的原子动作不是聊天消息的 Ack。

被问「会不会丢」时，按发送失败、进程死亡、重复、乱序四件事分别说靠什么，不说「TCP 所以不会丢」。被问最难的客户问题时，按现象、日志、根因、修复、文档来讲一个真实 case；没有就讲分类方法，不编客户名。

## 例子（至少 1 个完整代码或伪代码块 + 边界场景）

发送先落库，接收按序号补洞。重连成功后从本地最大连续序号往后拉：

```kotlin
class MessagePipeline(private val db: MessageDao, private val api: ImApi) {
    private var connectedSeq = 0L

    suspend fun send(text: String) {
        val local = db.insertSending(text)
        try {
            val ack = api.send(local.clientId, text)
            db.markAcked(local.clientId, ack.seq)
        } catch (e: IOException) {
            db.markFailed(local.clientId) // 仍留在会话里，可重试
        }
    }

    suspend fun onPush(msg: Incoming) {
        if (db.exists(msg.seq)) return
        db.insert(msg)
        val next = db.maxContiguous()
        if (msg.seq > next + 1) api.pull(from = next + 1, to = msg.seq)
    }

    suspend fun afterReconnect() {
        api.auth()
        api.pull(from = db.maxContiguous() + 1, to = null)
        connectedSeq = db.maxContiguous()
    }
}
```

边界一：Ack 丢失，发送侧超时重发，服务器其实已经有这条 clientId。服务器按 clientId 幂等，返回原来的序号；接收侧 exists 为真，不再插第二条。没有 clientId 的话，重发会变成两条内容一样的消息。

边界二：先收到序号 20，本地连续只到 17。如果不补拉，界面要么空出 18、19，要么把 20 直接接在 17 后面。应补拉 18 到 20，已有的 20 去重。

边界三：网络恢复时所有客户端固定 1 秒后重连。接入超时升高，鉴权失败被误当成密码错误。退避加抖动，并把 401 和超时分成不同错误码。

边界四：推送里带了消息正文就直接插入会话。和随后补拉的同一条重复，而且还可能是旧通知点开来的。通知只作唤醒，以补拉和长连接的序号为准。

## 画面（text 结构图）

```text
解析地址 → 建连 → 鉴权 → 同步离线 → 在线
                                    │
                     心跳超时或读失败 │
                                    ▼
                              退避 + 抖动 → 再走鉴权 → 按序号补拉

发送
  本地插入(发送中) → 写出 → 业务 Ack → 已送达
                    └超时→ 失败入队 → 重发（对端按 clientId 幂等）

接收
  推送或长连接
    → 序号已存在则丢弃
    → 出现空洞则补拉
    → 入库 → 按序号上屏

推送只负责唤醒，不负责作为唯一副本
主干一套；客户差异走配置和扩展点
```

## 常见坑与追问（至少 3 条）

1. **TCP 已经可靠，为什么还会丢消息？** TCP 不保证对方已经入库。进程在读出之后、落库之前崩溃，字节已经被确认，消息仍丢。所以要业务 Ack、本地发送队列和重连后的补拉。

2. **为什么界面不能等 Ack 再显示？** 弱网下 Ack 很慢，用户以为没点上。应先显示发送中，成功和失败再改状态。本地先入库，进程被杀后这条未发送的消息还在。

3. **重发会不会刷出重复消息？** 会，除非接收侧按序号或 clientId 去重，服务器按同一个 clientId 幂等。只做重发不做去重，弱网会话里会看到两条一样的内容。

4. **断网之后谁来发起重连？** 系统网络回调可以立刻试一次，心跳超时也可以进入重连。两者要进同一个状态机，并用指数退避加抖动，避免网络恢复时所有客户端同时打满接入层。连上之后重新鉴权并补拉，不假设旧缓冲还在。

5. **一家客户要改协议，为什么不开分支？** 上千家客户如果各复制一套连接，丢消息的修复合不回去。差异放配置和扩展点。日志回捞用开关、脱敏和体积上限定位这一家的问题，而不是把正文打进日志。

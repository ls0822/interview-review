## 一句话

离线包把 H5 资源提前准备好：能差分就差分，要加密就加密，下载后校验，替换失败就回滚，并用 Push 在打开前预处理。上传则是有界队列里的分片并发，按业务调度，用 MD5 采样发现传坏的片。两条都用成功率和分层耗时说话，而不是用「改成了多线程」。

## 组成与结构

离线包的状态：

```text
空闲 → 取任务（差分或全量）→ 下载 → 校验
        → 解密（如果加密）→ 原子替换 → 成功
        任一失败 → 丢掉临时文件，旧版本继续可用
        过期或不用 → 清理
```

上传的状态：

```text
入队（有界）→ 按权重取得并发槽 → 从已确认偏移传下一片
        → 片校验通过 → 偏移前进
        → 整文件校验通过 → 成功
        超时 → 退避后续传
        业务拒绝 → 失败回调，不盲目重试
```

材料里的结果口径：

| 数字 | 含义 |
|------|------|
| 离线包 3 日成功率约 99.4% | 按三日窗口，不是单次请求 |
| 插件包约 99.9% | 另一条包，不和离线包合成一个数 |
| H5 使用率约 +20% | 资源就绪之后的使用变化 |
| 上传小文件约 +8%、大文件约 +15% | 按大小分层，相对重写之前 |

快传侧的背景是亿级日活 App 里的基础 SDK，和跨部门治理放在一起讲：核心库发版频率下降，业务才能独立迭代这些 SDK。日活不要说成个人用户数。

Push 预处理是在用户打开之前把包拉到本地，减少打开后的等待。预处理失败不能挡住打开之后的正常下载。

## 原理（深度，分步骤，讲清为什么）

**1. 为什么要差分，又为什么要能退回全量**

全量包大，失败一次要重下的字节多，流量和成功率都差。本地已经有上一版时，只下补丁再打上去，字节少。前提是基线版本确实是补丁所对应的那一版。本地没有基线、基线被清掉、或者补丁本身比全量还大，就改下全量。硬打补丁会得到一个既不是旧版也不是新版的目录。

**2. 为什么先校验再替换**

CDN 返回 200 只说明连接结束了，内容可能被截断，也可能下到了错误版本。先对摘要。不一致就删掉临时文件，正在使用的旧包不动。摘要要和版本一起从可信接口来，不能只信包内部自带的那一份，否则谁改包谁就能改那份摘要。

加密包是在校验通过之后再解密。先解密再校验，会把损坏的密文解出一堆垃圾还写进目录。钥匙走可信通道，不写死在包里的常量。传输本身仍是 HTTPS。加密解决的是落地之后的内容保护，TLS 解决的是路上不被看。两件都要，互相不替代。

**3. 原子替换和回滚**

下载写在临时文件或临时目录。成功后用一次替换把「当前版本」指到新目录。替换进行到一半进程被杀，下次启动应看到旧版本仍完整，临时目录可丢弃，而不是把半个新目录当成当前版本。做不到原子的文件系统操作，就要先写标记「新版本未就绪」，就绪标记最后写。启动时标记不在就删临时数据。

过期包要清理，但不能清掉当前正在用的基线，否则下一次差分没有基线。

**4. 上传为什么是分片加有界队列**

一个大文件一次写出，失败就从 0 开始，弱网上几乎无法完成。分片之后，已确认的偏移留下，失败从偏移继续。并发可以把带宽打满，但要有上限：并发过高时每片都超时，成功率下降。小文件和大文件要分开看，小文件的时间多半在握手和调度，大文件才在传输，所以提升幅度不一样，大约是小文件 8 个点、大文件 15 个点。

多业务共用一条上传时，如果谁先到谁占满并发，后台日志会把用户正在等的图片堵住。队列要有权重，并且有界。队列满了立刻失败回调，让业务决定丢弃还是稍后再入队，而不是无限制占内存。

**5. MD5 采样在查什么**

它查的是这一片传到服务器之后还是不是原来的字节，用来发现传输损坏。可以每片都算，也可以按策略采样；整文件再对一次，防止片序错了但每片自己是对的。MD5 在这里是校验和。它不是密码存储，也不代替 HTTPS。对不齐就重传这一片，不要报成功。

**6. 预处理和打开后的下载是同一条状态机**

Push 到了就入队下载，优先级可以低于用户正在打开的那一次。打开时如果预处理已成功，直接用本地包。如果预处理下载到一半，打开后的请求应接上同一偏移，而不是再下一次全量。两套下载器会把同一个包下两次，还可能互相替换。

防盗链过期是 403，要重新要 URL，不要把 403 当成超时去换 IP 重试。这和 CDN 那套失败分类是同一件事。

同一个包 id 同时只允许一个下载任务，Push 预处理和用户打开附着到同一次偏移上。

## 使用与实践

指标先分层再优化：离线包看 3 日成功率、校验失败占比、差分转全量的比例；上传看大小分层的成功率、分片超时、队列等待时间。没有这些数，就不同时改并发和差分。

A/B 或版本对比要说样本、网络类型和端版本。只在办公室 Wi-Fi 上看到变快，不能说大文件提升了 15 个点。15 和 8 是材料里的结果，讲述时带上「小文件 / 大文件」这层。

和治理的关系：离线包和上传是基础 SDK。接口稳定之后，业务不必为了改自己的页面去发核心库。发版频率下降大约 90% 讲的是核心库，不要说成离线包本身的发布次数。

插件包是另一条：宿主和插件的 API、资源要兼容，keep 规则防止混淆把插件要的类删掉。99.9% 是插件包的口径。现在不做绕过审核的热修，只讲兼容检测和 keep。

线程：下载和哈希不要在主线程。SDK 的同步方法如果会读大文件，宿主一调用就 ANR。对外是入队和回调，回调线程写清楚。

## 例子（至少 1 个完整代码或伪代码块 + 边界场景）

离线包校验通过才替换。上传从确认过的偏移继续，队列有上限：

```kotlin
suspend fun install(task: PackageTask, files: LocalStore) {
    val baseOk = task.patch == null || files.versionIs(task.baseVersion)
    val download = if (baseOk && task.patch != null) task.patch else task.full
    val tmp = http.download(download.url, files.tempFor(task.id))
    if (sha256(tmp) != download.digest) {
        tmp.delete()
        return // 旧版本还在
    }
    val ready = if (download.encrypted) decrypt(tmp, task.key) else tmp
    files.replaceAtomically(task.id, ready)
}

class UploadQueue(private val slots: Int, private val maxWaiting: Int) {
    private val waiting = ArrayDeque<Upload>()

    fun enqueue(task: Upload): Boolean {
        if (waiting.size >= maxWaiting) {
            task.callback.onFailed(QUEUE_FULL)
            return false
        }
        waiting += task
        pump()
        return true
    }

    private fun pump() {
        while (running < slots && waiting.isNotEmpty()) {
            val task = waiting.removeFirst()
            running++
            scope.launch(Dispatchers.IO) {
                var offset = task.ackedOffset
                while (offset < task.size) {
                    val part = task.readPart(offset)
                    if (md5(part) != http.putPart(task.id, offset, part)) break
                    offset += part.size
                    task.ackedOffset = offset
                }
                running--
                pump()
            }
        }
    }
}
```

边界一：校验失败仍执行替换。坏包变成当前版本，下次启动 H5 白屏，而且差分基线也坏了。校验失败只能删临时文件。

边界二：替换过程中被杀。启动时看到未完成标记，删掉半成品，继续用旧目录。不能把「临时目录非空」当成安装成功。

边界三：上传并发开得很大，弱网每片超时，已确认偏移不前进，成功率下降。槽位要有上限，并按网络降并发。大文件才从并发得益。

边界四：队列无界，业务在循环里入队大文件。内存涨，最后低内存杀进程，所有偏移如果没落盘就从头再来。队列有界，偏移落盘，失败有回调。

边界五：Push 预处理和打开页面各启动一次全量下载，互相覆盖临时文件。同一个包 id 只能有一个进行中的任务，后来的请求附着到已有任务上。

**错误对照：** 错法摘要校验失败仍 `replaceAtomically`，H5 白屏且差分基线损坏。对法：失败只删临时文件，保留旧版本；上传队列有界，已确认 `offset` 落盘再继续。

## 画面（text 结构图）

```text
离线包
  有基线且补丁有效 → 下补丁
  否则 → 下全量
       → 摘要
       → 解密（若需要）
       → 原子替换
  失败：临时文件删除，旧版本仍在
  Push 预处理 = 提前进入同一条状态机，失败不挡住打开后的下载

上传
  多业务 → 有界队列 → 按权重取槽位
        → 分片从已确认偏移继续
        → 片 MD5，整文件再校验
  超时退避；4xx 和校验失败不按「立刻再来一次」处理

口径分开
  离线包 3 日约 99.4%
  插件包约 99.9%
  上传小文件约 +8%，大文件约 +15%
```

## 常见坑与追问（至少 3 条）

1. **差分失败了为什么还要全量？** 没有正确基线时补丁打出来的不是新版本。全量是退路。正在使用的旧包在新包校验并替换成功之前一直留着，所以失败不会把用户打到白屏。

2. **为什么下载完不能直接解压覆盖？** 覆盖到一半进程被杀，目录里是半个新包加半个旧包，下次也无法再当基线。应写临时位置，校验和解密都成功后一次替换，并有未完成标记供启动时清理。

3. **分片并发是不是越大越好？** 不是。带宽和超时决定上限。过高时每片都失败，已确认偏移不前进。小文件的收益也比大文件小。材料里的提升要分开说：小文件大约 8 个点，大文件大约 15 个点。

4. **MD5 采样能不能说明传输是安全的？** 它说明这一片字节和大概率没有传坏。防窃听靠 HTTPS，防伪造要看摘要是否来自可信接口。密码存储更不能用 MD5。对不齐的片重传，不把整次上传报成功。

5. **预处理和用户打开各下各的会怎样？** 同一包两个任务写同一个临时文件，互相截断，校验永远失败。一个包 id 只保留一个进行中任务，Push 和打开附着到同一次下载，共享偏移。

## 一句话

教育直播底座只负责房间生命周期和信令，RTC 放在适配层后面可以替换。课件、白板、上下台按产品插上去。切班对用户是不停课，对实现是一次原子动作：多来源信令先入队，失败就滚回切班前。

## 组成与结构

```text
业务（课件、白板、上下台、小学 Compose 工具条）
        │ 只依赖房间和信令
        ▼
底座：进房、房间状态、信令通道
        │
        ▼
RTC 适配：进房 / 推拉流 / 回调
        │
        ▼
具体 RTC SDK
```

小学界面再叠一层：底层课件是 H5 或 Cocos，用 `AndroidView`；中间是数字人和动画；上层是 Compose 工具条。房间、页码、连麦是状态，信令改状态，Compose 重组。数字人的声音在 RTC 里，课件翻页靠 SEI 对齐，关键节点另有可靠补发。

职责口径：Android SDK 的结构，以及房间、信令这条主链路。模型算法不是这条链路里的工作；MNN 是工程集成、联调、性能观察和建议。排查 Agent 是另一条线：拉日志、对源码、给初判，人确认后再改。

## 原理（深度，分步骤，讲清为什么）

**1. 为什么课件不进底座**

课件、白板、上下台的变更比「房间还在不在」频繁，而且初中和小学不一样。写进底座之后，每加一个教学工具都要改底座、回归所有产品。拆出去之后，底座保持房间和信令，产品线只插自己的模块。伪直播从大约 3 天收到 1 天，切班扩展从大约 10 天收到 3 天，靠的是模块复用，不是把需求都塞进同一个库。

**2. 适配层里有什么、没有什么**

业务调用的词只有进房、推拉流、静音、离开和回调。适配实现把某一家 RTC 的状态映射成这组词。换供应商时替换实现，回归用例打在适配层：进房失败、断线、权限拒绝，而不是把每个页面重测一遍。

适配层不包含课件翻页和班级状态。那些走信令。混进去之后，换 RTC 就要回归教学逻辑，适配层就变成第二个底座。

**3. 无感知切班到底切什么**

用户侧不停课，看到的还是教室。实现上要换的是班级资源和状态，例如目标班、成员和这一班的课件上下文。它不是把 Activity 销毁重进，也不是把 RTC 房间无故拆掉再建一次。能保持的媒体连接就保持，必须重建的要在状态机里写成一步，而不是页面上散落几次调用。

**4. 为什么信令要入队，而且还要原子**

切班会碰到多个服务。到达顺序不稳定：可能先收到「新班资源就绪」，后收到「开始切」，也可能相反。如果来一条执行一条，状态会先跳到一半，再被另一条打回去。

做法是进一条队列，按序执行一个原子动作。原子是说：这一次切班要么完整生效，要么回到切班前的状态。超时、重试有上限。超过上限就回滚，并打点告警。不要无限重试，重试会把半个新班和半个旧班叠在一起。

状态可以记成：空闲、切班中、成功、失败回滚。切班中不再接受第二下切班，后来的请求排队或拒绝，避免两个原子交叉。

**5. SEI 为什么不能单独承担翻页**

数字人的音画在 RTC 流里，课件翻页如果只写在 SEI 里跟着流走，丢包或延迟时就会错页，声音已经说到下一页，课件还停着。SEI 适合对齐，不适合作为唯一的可靠指令。关键页码要有信令补发。信令到了就校正当前页，SEI 负责时间上的贴合。两路都丢时，界面停在最后一页已知状态并打点，而不是猜一页。

**6. 成功率和那 1% 怎么说**

进房和切班大约 99%，一期 Android 灰度大约 4.5 万人次，没有 P3 及以上事故。这 99% 的时间窗、端、是否把重试成功算进去，要先说清楚。失败的那约 1% 按网络、鉴权、RTC、资源下载分类进监控，不把重试成功记成一次失败。

小学含动态下载是大约 95%，初中进房大约 98%。95 和 99 不是同一个口径：前者把模型和动画下载算进结果。动态下载用队列、优先级和超时，能和进房并行，但下载拖垮进房时要能降级占位，而不是堵死房间状态机。

Agent 的正确率大约 80% 到 90%，耗时降 90% 以上。边界是日志加源码的初步分析，人确认后再改。不要把正确率说成自动修复率。

切班中的第二条请求不能再开一个原子动作。后来的目标班排队或直接拒绝，等当前这次成功或回滚后再处理。快照在开始切时记下，超时和失败都回到这份快照，避免新班资源写了一半又叠上旧班状态。信令带序号，旧的页码不能覆盖新的页码，SEI 只做对齐。动态下载和进房可以并行，但 95% 和 99% 的口径分开报，下载失败用占位，不把房间状态机打回未连接，除非产品规定进房必须包含资源就绪。

适配层只翻译进房、推拉流和回调。课件翻页走信令，不写进 RTC 适配，否则换供应商要回归教学逻辑。MNN 只讲工程集成和性能，模型效果归算法。Agent 是初判，人确认后再改，正确率不是自动修复率。

失败的大约 1% 按网络、鉴权、RTC、资源下载分类。重试成功不记成一次失败。灰度大约 4.5 万是 Android 人次。

伪直播大约从 3 天收到 1 天，切班扩展大约从 10 天收到 3 天，靠的是模块复用。

没有 P3 及以上事故要和成功率口径一起说。

## 使用与实践

口述按六步：背景、职责、方案三层、切班取舍、数字口径、一个线上失败分类。八到十分钟，不要先讲排期。

被问到 Bridge：方法白名单、参数校验、线程切回主线程或 ViewModel，不做任意反射。被问到 Compose：工具条收集状态，课件在 `AndroidView` 里，不需要的区域把触摸放下去。被问到保活：不讲拉起。房间断线就按长连接退避重连。

MNN 只讲集成和性能观察。模型效果归算法。so 要注意 16KB 对齐，第三方 RTC 的库也要查。

准备一张失败分类的例子：指标上某类错误升高，日志对上是鉴权过期或资源超时，修的是重试上限或下载优先级，回归用同一类 case。没有具体事故就不要编一个百分比。

## 例子（至少 1 个完整代码或伪代码块 + 边界场景）

切班串行执行，失败回到快照。第二下来时如果还在切，就排队：

```kotlin
class SwitchClass(private val signal: SignalQueue) {
    private val state = MutableStateFlow(Idle)
    private var snapshot: RoomSnapshot? = null

    suspend fun request(target: ClassId) {
        signal.send(Switch(target)) // 和别的信令同一条队列
    }

    suspend fun drain() {
        for (cmd in signal.incoming) {
            when (cmd) {
                is Switch -> {
                    if (state.value is Switching) continue
                    snapshot = room.capture()
                    state.value = Switching
                    val ok = withTimeoutOrNull(LIMIT) { apply(cmd.target) } != null
                    if (ok) state.value = Idle
                    else {
                        room.restore(snapshot)
                        state.value = RolledBack
                        report("switch_rollback")
                    }
                }
            }
        }
    }
}
```

边界一：资源就绪的信令比「开始切」先到。不入队的话会把资源装到旧班上。入队之后按业务序号或在原子动作内部再检查阶段，先到的就绪先记下，等开始切再使用，而不是立刻生效。

边界二：切到一半超时，新班资源已经写了一半。没有快照就会停在混合状态。回滚用切班前的快照，并限制重试次数。回滚失败要告警，留在失败态，不要假装已经成功。

边界三：SEI 先把课件翻到第 5 页，可靠信令因为延迟后到，仍写着第 4 页。如果信令无条件覆盖，会把页翻回去。信令要带序号或版本，旧版本不能覆盖新版本。SEI 丢了则靠信令把页校正过来。

边界四：把动态下载失败算进 99% 的进房失败。口径被放大，和初中进房无法比较。小学含下载用 95% 这条，纯房间用 99% 这条，监控分开。

## 常见坑与追问（至少 3 条）

1. **为什么不把课件放进底座，少一次模块跳转？** 课件的变更频率和产品差异都更大。放进去之后初中和小学无法共用底座，每加一个工具都要改核心库。底座只留房间和信令，工期从大约 10 天收到 3 天靠的是这种复用。

2. **无感知是不是网络无感、实现上什么都没切？** 不是。用户侧不停课。实现上要换班级资源和状态，并且这次替换是原子的。失败要回到切班前，而不是留下半个新班。

3. **多服务信令乱序怎么处理？** 不按到达顺序直接改状态。进队列，按序做原子切班。超时和重试有上限，失败回滚并打点。切班进行中不开始第二个原子动作。

4. **SEI 丢了会怎样？** 可能错页或延迟。SEI 负责对齐，关键页码要有可靠信令补发。信令也要带序号，避免旧页把新页盖掉。

5. **99% 和 95% 为什么不一样？** 进房切班大约 99%。小学把动态下载算进去大约 95%，初中进房大约 98%。不能合成一个成功率。失败的部分按网络、鉴权、RTC、资源分类，重试成功不记成失败。
